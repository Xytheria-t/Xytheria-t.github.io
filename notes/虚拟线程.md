## 平台线程 vs 虚拟线程

| 对比项 | 平台线程 | 虚拟线程 |
|---|---|---|
| 底层载体 | 每个线程 = 一个 OS 线程 | JVM 对象，映射到少量 OS「载体线程」 |
| 栈 | 固定（常 1MB），受内存上限 | 动态，可百万级同存 |
| 创建 / 销毁 | 走内核，开销大 | 纯用户态，近普通对象 |
| 阻塞代价 | 占住 OS 线程，白白等 | 自动让出载体，去跑别的任务 |
| 调度者 | OS 调度器 | JVM 调度器 |
| 状态 API | 全状态可见 | 只报 NEW / RUNNABLE / TERMINATED |

> [!note] 与线程创建的关系
> 平台线程怎么生出来、任务体怎么写见 [[线程创建]]——虚拟线程仍以 `Thread` 表达任务体，只是不再一任务一 OS 线程。

> [!note] 定位
> 面向 **IO 密集 + 海量任务**（每请求一线程模型）的解法：让「线程数」不再是瓶颈。CPU 密集与重度锁争用场景没有收益，见下。

## 调度原理

> [!tip] 轻量来自「阻塞不占坑」
> 平台线程阻塞在 IO / `park` 上会占住 OS 线程；虚拟线程阻塞时 JVM 把它**摘下（unmount）载体**，载体立刻转去执行别的虚拟线程——这就是上万虚拟线程只靠几十个载体线程的真相。

> [!warning] pinning：synchronized 会让载体被钉住
> 虚拟线程在 `synchronized` 块内阻塞时，载体被该线程**钉住（pinned）**，无法让出——JDK 21 仍如此。高争用或长阻塞的临界区用 `ReentrantLock`（不 pin）；JDK 24 起（JEP 491）才解除 synchronized 钉住。

## 创建方式

| API | 形态 | 适合 |
|---|---|---|
| `Thread.ofVirtual().start(task)` | 单个虚拟线程 | 少量 / 组合结构 |
| `Executors.newVirtualThreadPerTaskExecutor()` | 每任务一线程的 ExecutorService | 批量 IO 任务，替代 `new Thread` |

> [!warning] 别再套线程池参数
> 虚拟线程按任务即建即弃，**不需要 core / max / 队列**；给它配池参数反而违背设计。默认 `newVirtualThreadPerTaskExecutor` 已够，吞吐由任务量自然撑起。

```java
// 方式一：单线程
Thread vt = Thread.ofVirtual().name("fetch-").start(() -> doIO());

// 方式二：每任务一线程（推荐，批量 IO 场景）
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (String url : urls) {
        executor.submit(() -> fetch(url));   // 一万个 URL = 一万个虚拟线程
    }
} // try-with-resources 自动关闭并等待全部完成
```

> [!tip] 关闭语义
> `newVirtualThreadPerTaskExecutor` 实现 `AutoCloseable`，try 块结束即 `close()`（等待已提交任务完成后关闭），退出机制干净，无 shutdown 噩梦。

## 适用场景

```branch
01: 任务类型
02: 按特征分流
- IO 密集 + 海量并发 | 虚拟线程 | 每请求一线程
- CPU 密集 | 平台线程 + 池 | 无收益，虚拟线程不加算力
- 高争用 synchronized | 先换 ReentrantLock | 避免 pinning
- 有界资源（DB 连接 / 下游限流） | 信号量限流 | 虚拟线程不解决资源上限
- 延迟敏感小任务 | 平台线程池 | 虚拟线程调度有额外开销
```

> [!danger] 有界资源仍需限流
> 虚拟线程消除了线程数上限，但**连接池 / 下游 QPS 上限还在**。无脑开万级并发打 DB 或第三方，等于把雪崩从「线程 OOM」挪到「打爆下游」。用 [[Java 锁对比]] 里的 Semaphore 共享同步器对比,或池本身做反压。

> [!note] 结合点
> 线程池的调参与拒绝策略适用于**平台线程**（[[线程池创建]]）；虚拟线程把「并发度」从池参数里解放出来，改由资源限流决定。

<details>
<summary>面试问答 (4题)</summary>

Q：虚拟线程和平台线程的本质区别？

A：平台线程一线程一 OS 线程、栈固定约 1MB，数量受内存限制；虚拟线程是 JVM 管理的轻量对象，映射到少量载体线程，阻塞时自动摘下让出载体，因此能支撑百万级并发任务，创建销毁也远便宜。

Q：虚拟线程为什么能扛那么多并发？

A：关键在「阻塞不占坑」。IO / park 阻塞时 JVM 把虚拟线程从载体上摘下，载体立刻执行别的虚拟线程，OS 线程数量保持在几十个量级，不再随任务数线性增长。

Q：什么场景用虚拟线程，什么场景不用？

A：用：IO 密集、海量并发任务（HTTP 调用、DB 访问、每请求一线程的服务）。不用：CPU 密集计算（不加算力反增调度开销）、高争用 synchronized（pinning 钉住载体），有界资源场景必须额外限流。

Q：有了虚拟线程还需要线程池吗？

A：需要。虚拟线程适合「任务数大、各自阻塞」的形态；CPU 密集、需排队限流的场景仍用平台线程池（[[ThreadPoolExecutor]]）。且虚拟线程不解决下游资源上限，DB / 第三方调用仍要信号量或连接池反压。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：虚拟线程能提高 CPU 密集任务吞吐。它不加算力，密集计算场景收益约等于零，还有调度开销。
- 误区：虚拟线程数量随便开。并发数受下游资源约束，无界打 IO 是把雪崩从本地线程转移到远端服务。
- 误区：synchronized 也能放心用在虚拟线程里。阻塞时 pinning 钉住载体线程，JDK 21 仍如此；临界区优先 ReentrantLock。

</details>
