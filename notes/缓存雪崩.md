# 缓存雪崩

## 思维链路速查

```chain
现象定义 | 大量 key 同时失效 | 区分
成因与危害 | 瞬时 DB 压力 | 核心
解法全景 | 错峰/多级/降级/预热 | 策略
三场景对比 | 见 MOC | 关联
面试问答 | 高频考点 | 复盘
```

雪崩 = 大量 key 集中过期或缓存层整体不可用 → 请求穿透到 DB，DB 被打垮。它与 [[缓存击穿]]、[[缓存穿透]] 同属缓存引发的典型异常，差异只在「失效范围」：击穿是单点、穿透是无此物、雪崩是一片。

## 现象定义

| 概念 | 触发场景 | 影响范围 | 根因 |
|---|---|---|---|
| 缓存雪崩 | 大量 key 同时过期 / Redis 宕机 | 大面积 | 过期时间集中或缓存层不可用 |
| 缓存击穿 | 单个热点 key 失效 | 单点 | 热点 key 并发重建 |
| 缓存穿透 | 查不存在的 key | 单点 | key 本身不存在，无缓存可命中 |

> [!important] 心法
> 雪崩的本质不是「某个 key 丢了」，而是「同一时刻丢一片」或「缓存层整体失效」。解法核心：别让失效/不可用同时发生，即便发生也要兜底不打垮 DB。

## 成因与危害

```chain
集中设置 TTL | 同一批写入 | 同时过期
热点聚集 | 促销 / 零点 | 峰值叠加
缓存层宕机 | 内存满 / 网络分区 | 全量 miss
连锁恶化 | 响应变慢 → 重试加压 | 正反馈
```

| 成因 | 典型场景 | 危害 |
|---|---|---|
| 批量 key 同 TTL | 定时任务批量回写缓存、统一过期 | 到点后请求全落 DB |
| 时钟漂移 / 批量刷新 | 服务重启后统一预热 | 集中重建 |
| 缓存层不可用 | 宕机 / 网络割裂 | 全量回源 |

> [!warning] DB 连锁恶化
> 雪崩时 DB 被打满 → 响应变慢 → 业务线程堆积 → 超时重试 → 进一步加压，形成正反馈，最终拖垮整个系统而非单库。

## 解法全景

```chain
错峰过期 | 加随机抖动 | 预防
熔断降级 | 限流/降级 | 兜底
预热与容量 | 提前加载 | 抗峰
```

| 方案 | 做法 | 防什么 | 代价 |
|---|---|---|---|
| 错峰 TTL | 基础 TTL + 随机 jitter（如 ±5min） | 集中过期 | 几乎无 |
| 二级缓存 | 本地缓存 + Redis，本地兜底 | Redis 宕机 | 一致性稍弱 |
| 熔断 / 限流 | DB 侧限流、熔断，超出拒绝或降级 | DB 被打垮 | 部分请求失败 |
| 缓存预热 | 启动 / 大促前主动加载热点 | 冷启动峰值 | 需预判热点 |
| 高可用 | Redis 主从 + 哨兵 / 集群，避免单点不可用 | 缓存层整体失效 | 运维成本 |

> [!tip] 最划算的两招
> 错峰 TTL（随机过期）几乎零成本，先上；再叠加缓存层高可用（主从/集群）兜底整体失效。其余按需。

> [!note] 关于「互斥重建」
> 互斥锁 / singleflight 是「同一个 key 并发回源」的合并手段，本质是 [[缓存击穿]] 的解法（单点并发重建）。雪崩场景下同一时刻丢一片 key，但每个 key 通常只是被自身请求回源一次，单飞收益小、实现复杂度高，不列为核心方案；只有「雪崩撞上热点击穿」时才叠加使用。

## 三场景对比

| 异常 | 治的是 | 核心手段 | 详见 |
|---|---|---|---|
| [[缓存雪崩]] | 一片（集中失效 / 宕机） | 错峰 TTL / 多级缓存 / 熔断 | 本篇 |
| [[缓存击穿]] | 一点（单热点失效） | 互斥重建 / 逻辑过期 | 失效范围最小，单点即可搞定 |
| [[缓存穿透]] | 无此物（key 不存在） | 布隆过滤器 / 空值缓存 | 与过期无关，锁和错峰都无效 |

> [!note] 一眼区分
> 三者的差异只在**失效范围**：雪崩是「一整片同时没了」，击穿是「一个热点没了」，穿透是「压根没这个东西」。范围判断错了，手段必然错配——用互斥锁防雪崩，挡不住缓存层整体宕机。

<details>
<summary>面试问答 (3题)</summary>

Q：缓存雪崩和缓存击穿的区别？

A：雪崩是大量 key 同时失效或缓存层整体不可用，影响面大；击穿是单个热点 key 失效，大量并发打到同一数据。前者靠错峰 TTL + 熔断，后者靠 mutex/singleflight。

Q：怎么预防缓存雪崩？

A：基础 TTL 加随机抖动避免集中过期；缓存层做高可用（主从/集群），本地缓存兜底整体宕机；DB 侧限流熔断保护；大促前预热热点。

Q：Redis 真的挂了怎么办？

A：多级缓存（本地兜底）+ 熔断降级，读降级直查 DB 并限流，避免请求雪崩冲击 DB；Redis 恢复后靠 TTL 自然重建。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：只给 key 设 TTL 就够了。同步批量写入会导致同时过期，须加随机抖动。
- 误区：雪崩 = 击穿，解法一样。雪崩是「一片」、击穿是「一点」，前者需错峰，后者需互斥。
- 误区：加互斥锁一定好。锁保护热点重建，但解决不了「缓存层整体宕机」，还需多级缓存 + 降级。

</details>
