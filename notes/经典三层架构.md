# 经典三层架构

## 思维链路速查

```chain
三层定义 | 各层职责边界 | 概览
依赖方向 | 上层依赖下层与解耦 | 核心
与 MVC 辨析 | 架构分层 vs 表现层模式 | 厘清
落地：Spring 骨架 | 构造注入分层 | 实战
面试问答 | 高频考点 | 复盘
```

三层的本质是「职责分区 + 单向依赖」：上层调下层、靠接口解耦；易混的是它与 MVC 的分工——MVC 只是表现层内部的组织方式。

## 三层定义

| 层 | 别名 | 职责 | 典型组件 |
|---|---|---|---|
| 表现层 | 表示层 / UI / Web | 接收请求、参数校验、组装响应 | Controller、View、DTO |
| 业务逻辑层 | 服务层 / Service | 业务规则、事务编排、领域计算 | Service、Manager、Domain |
| 数据访问层 | 持久层 / DAO | 数据增删改查、与 DB / 外部存储交互 | DAO、Mapper、Repository |

- **跨层模型**：DO / POJO / DTO 在层间传输；贫血模型（字段 + getter/setter）最常见，充血模型把行为放进实体，归 DDD。
- **分层动机**：单一职责、解耦、下层可替换、上层可独立单测（mock 下层）；极简 CRUD 可不分层。

## 依赖方向

依赖单向向下：表现层 → 业务层 → 数据层，下层**绝不**反向依赖上层；存储与索引设计见 [[MySQL 索引]]。

- **面向接口编程 + 依赖倒置（DIP）**：上层定义并持有下层接口、下层实现、运行时注入（Spring `@Autowired`）。
- **收益**：换下层实现零改上层；单测 mock 下层。

> [!tip] 面向接口正是 AOP 的土壤
> Spring 声明式事务、缓存注解都挂在 [[动态代理]] 上；业务层脱离接口、`this.xxx()` 自调用时这些注解会集体失效。

## 与 MVC 辨析

| 维度 | 经典三层架构 | MVC |
|---|---|---|
| 视角 | 系统级纵向职责分层 | 表现层内部设计模式 |
| 覆盖范围 | 表现 + 业务 + 数据 | 仅表现层（Model-View-Controller） |
| 关系 | MVC 的 Controller 属于三层中的表现层 | 解决「界面与交互如何组织」 |

> [!danger] 高频混淆
> 把 MVC 当三层：误以为 M=数据层、V/C=表现层。实际 MVC 的 Model 常是领域模型，归属业务 / 表现。

## 落地：Spring 骨架代码

构造注入骨架（生产中业务层 / 数据层建议抽接口 + Impl）：

```java
@RestController
public class OrderController {
    private final OrderService service;
    public OrderController(OrderService s) { this.service = s; }
    @PostMapping
    public OrderDTO create(@RequestBody OrderDTO dto) { return service.create(dto); }
}

@Service
public class OrderService {
    private final OrderRepository repo;
    public OrderService(OrderRepository r) { this.repo = r; }
    @Transactional
    public OrderDTO create(OrderDTO dto) { return repo.save(dto); }
}

@Repository
public class OrderRepository {
    public OrderDTO save(OrderDTO dto) { return dto; }       // JDBC / MyBatis / JPA
}
```

- **演进方向**：贫血三层在复杂域会膨胀为「事务脚本」；DDD、六边形、微服务按需引入。

<details>
<summary>面试问答 (1题)</summary>

Q：三层架构和 MVC 有什么区别？

A：三层是系统级职责分层（表现 / 业务 / 数据），MVC 只是表现层内部的模式，二者不互斥。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：每层都必须有。简单 CRUD 硬套三层是过度设计。
- 误区：下层可以调用上层。反向依赖会破坏分层、形成循环依赖。
- 误区：业务逻辑写在 Controller 里。表现层沦为业务层，丧失可测性。

</details>
