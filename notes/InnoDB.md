# InnoDB

## 思维链路速查

```chain
引擎定位 | 为什么是 InnoDB | 起点
内存结构 | 四个部件与 Buffer Pool | 核心
磁盘层级 | 表空间 → 段 → 区 → 页 | 结构
双写缓冲 | WAL 之外的兜底 | 深度
面试问答 | 高频考点 | 复盘
```

改一行数据，InnoDB 并不去碰磁盘上的那一行，而是在内存里改它所在的 16KB 页，再把改动以顺序日志落盘（WAL，先写日志、数据页延后刷——见 [[MySQL 日志]]）——「随机 IO 换内存操作 + 顺序写」是贯穿它所有部件的同一笔账：Buffer Pool 是记账的内存账户，表空间 → 区 → 页的分层让落盘尽量连续，双写缓冲补上 WAL 管不到的那一种崩溃。它也是这一卷的底座：索引长在它的页里，事务跑在它的日志与锁上。

## 引擎定位：InnoDB 与 MyISAM

MySQL 5.5 起 InnoDB 取代 MyISAM 成为默认存储引擎，替换的理由全在这张表里：

| 维度 | InnoDB | MyISAM |
|---|---|---|
| 事务 | ✅ ACID，靠 undo / redo 落地（见 [[MySQL 日志]]） | ❌ 无事务 |
| 锁粒度 | 行锁（默认），并发写不同行不冲突 | 表锁，一次写锁住整张表 |
| 外键 | ✅ | ❌ |
| 崩溃恢复 | ✅ redo 重放 + undo 回滚 | ❌ 表可能损坏，需 repair |
| 索引叶子存什么 | 聚簇索引存整行，二级索引存主键值 | 非聚簇，叶子存行的物理地址 |
| COUNT(*) | 必须扫描（见下） | 表头维护行计数，无 WHERE 时直接返回 |
| 全文索引 | ✅（5.6 起） | ✅ |

> [!note] MyISAM 的 COUNT(*) 为什么快，InnoDB 为什么快不了
> MyISAM 在表元数据里存行数，`SELECT COUNT(*) FROM t`（不带 WHERE）直接读计数。InnoDB 不存行数——**并发事务各自可见的行集不同**，任何一个固定数字都必然对部分事务是错的，只能扫；官方口径是「遍历最小的可用二级索引，没有二级索引才扫聚簇索引」。也正因为如此，`COUNT(*)` 与 `COUNT(1)` 在 InnoDB 里没有性能差别。

> [!warning] 版本前提
> 5.5 起 InnoDB 是默认引擎，8.0 起连系统表也全部换成 InnoDB。今天问 MyISAM 是为了对照两者的能力边界，不是选型建议——它只活在历史表与只读归档里。

## 内存结构：四个部件

InnoDB 的内存区由四块组成，只有第一块是主战场，另外三块都是它的补丁：

| 部件 | 干什么 | 一句话记忆 |
|---|---|---|
| Buffer Pool | 缓存数据页与索引页，读写都先在这里发生 | 最该调大的参数 |
| Change Buffer | 把「目标索引页不在池里」的改动先记下，等页读入时再合并 | 只服务非唯一二级索引 |
| Adaptive Hash Index | 为频繁等值访问的页自动建内存哈希，省掉 B+ 树下探 | 默认开，高并发下可能反成争用点 |
| Log Buffer | redo 落盘前的中转站 | 刷盘策略见 [[MySQL 日志]] |

对应的磁盘侧则是表空间 → 段 → 区 → 页的分层（见下文），中间靠后台线程拉动：page cleaner 刷脏页、purge 线程清 undo、IO 线程读写页、主线程在空闲与慢关闭时合并 change buffer。

## Buffer Pool：读写在内存里发生

InnoDB 的最小读写单位是页（默认 16KB）：读一行要先把它所在的页读进 Buffer Pool，改一行也是在池里改，改完的页叫脏页、等后台刷回磁盘。走内存还是走磁盘差着好几个数量级，所以它是最该调大的参数：

| 配置 | 默认 | 怎么定 |
|---|---|---|
| innodb_buffer_pool_size | 128MB | 专用数据库机器可到物理内存的 80%（官方原话「up to 80%」）；账和 [[分库分表]] 里「热数据装得下就够用」是同一笔 |
| innodb_buffer_pool_instances | 8（池小于 1GB 时为 1） | 大池拆成多实例，减少并发访问池元数据的争用 |

池里的页按（表空间号，页号）定位，另有三条链表各管一段生命周期：

| 链表 | 装什么 | 作用 |
|---|---|---|
| free | 还没用上的空闲页 | 读入新页时从这里分配 |
| LRU | 已读入、可被淘汰的页 | 池满时从冷端淘汰 |
| flush | 脏页，按变脏先后排队 | 刷盘队列，checkpoint 推进靠它（见 [[MySQL 日志]]） |

### 改进 LRU：新页为什么插在中点

标准 LRU 把新页插到链表头，一遇到全表扫描就崩：扫描页只被访问一两次，却会把真正的热页一路挤出去，池子越用越冷。InnoDB 把链表切成两段，新页插在正中间：

```chain
读入新页 | 插在 young 与 old 的分界点 | 中点
短暂访问 | 时间窗内不晋升 | 防污染
反复访问 | 超时才升到 young 头部 | 真热页
淘汰 | old 尾部先出局 | 兜底
```

- 链表分 young（热端，约 5/8）与 old（冷端，约 3/8），分界比例由 `innodb_old_blocks_pct` 控制，默认 **37**（即 3/8）；新读入的页插在分界点（old 段头部），不是链表头。
- old 段里的页再被访问时，要**距首次访问超过 `innodb_old_blocks_time`（默认 1000 毫秒）**，才晋升到 young 段头部。
- 全表扫描时一个页往往在毫秒内被连续访问多次，全部落在时间窗内、晋升不了，扫描完就停在 old 段，很快从尾部淘汰——热页毫发无损。

> [!tip] 扫描频繁的库
> 大表全表扫描多时，把 `innodb_old_blocks_pct` 调小（官方举例调到 5），让「读一次就不再用」的数据最多只占池子的一小块。

### 预读与刷脏

- **线性预读**：一个区（64 页）中被顺序读到的页达到 `innodb_read_ahead_threshold`（默认 56，取值 0~64）时，异步预读**下一个区**，把顺序扫描提前变成连续 IO；随机预读（`innodb_random_read_ahead`）默认关闭。
- **刷脏**：8.0 由 page cleaner 线程负责，`innodb_page_cleaners` 默认 4（超过 buffer pool 实例数时自动对齐到实例数）。脏页占比过 `innodb_max_dirty_pages_pct_lwm`（默认 10%）开始提前刷，到 `innodb_max_dirty_pages_pct`（默认 90%）转为激进刷；自适应刷脏还会跟着 redo 生成速度调整刷多少，避免 redo 写满时被迫强刷（sharp checkpoint）造成卡顿（redo 循环写与 checkpoint 见 [[MySQL 日志]]）。
- `innodb_flush_neighbors` 在 8.0 默认为 0（不顺带刷同区相邻页，SSD 推荐）；5.7 默认为 1。

## Change Buffer：推迟二级索引的随机读

改一行的代价不止改数据页：每个二级索引都要跟着改，而这些索引页很可能不在池里。若为此把页从磁盘读进来，一次插入就变成好几次随机读。Change Buffer 的做法是先把改动记在内存里，等那个页因为别的原因被读进池时再合并（merge）：

| 项 | 内容 |
|---|---|
| 适用对象 | **非唯一二级索引**的 INSERT / UPDATE / DELETE 改动 |
| 生效前提 | 目标索引页不在 Buffer Pool 中 |
| 存在形式 | 内存里占 Buffer Pool 的一部分，落盘在系统表空间；改动同样记 redo，宕机不丢 |
| 合并时机 | 页被读入时、主线程空闲时、慢关闭时 |
| 上限 | `innodb_change_buffer_max_size` 默认 25（占池子百分比，最大 50） |

> [!note] 唯一索引为什么用不上
> 唯一索引写入必须**立刻**读页判重，页既然已经被读进来了，缓冲也就无从谈起——这正是「写多读少的表用普通索引更划算」的机理，选型对比见 [[MySQL 索引]]。此外，含降序索引列的二级索引也不支持缓冲（官方明列的限制）。

> [!warning] 合并的账迟早要还
> 官方提醒：受影响的二级索引多、改动量大时，merge 可能持续**数小时**，而且会在提交后继续、甚至跨重启进行。缓冲只是把随机读推迟合并，不是消灭它；`innodb_change_buffering` 可控制缓冲哪几类操作（默认 `all`，可选 `none` / `inserts` / `deletes` / `changes` / `purges`）。

## 自适应哈希索引：给热页抄近路

B+ 树查一行要 3~4 次页访问，InnoDB 会盯着索引页的访问模式：某个页的等值查找特别频繁时，自动用索引键的前缀在内存里为它建一份哈希，下次再查一次定位。

- 「自适应」= 建与删都由 InnoDB 自己判断，DBA 只能整体开关：`innodb_adaptive_hash_index` 默认 ON，并按 `innodb_adaptive_hash_index_parts`（默认 8，最大 512）分片减少争用。
- 只服务等值与直接定位；范围扫描、`LIKE '%x%'` 这类用不上。
- 官方明确提醒它可能反过来成为瓶颈：「heavy workloads, such as multiple concurrent joins」下访问哈希索引会变成争用源，且收益很难预先判断——结论要靠压测开、关各跑一遍。若 `SHOW ENGINE INNODB STATUS` 的 SEMAPHORES 段出现 `btr0sea.c` 的 rw-latch（读写锁）等待，就调大分片数或直接关掉。

## 磁盘结构：从表空间到页

InnoDB 的空间管理是层层套娃，每一层的划分都为同一个目的——让 IO 尽量连续：

| 层 | 单位 / 内容 | 为什么这么分 |
|---|---|---|
| 页 page | **16KB**，InnoDB 最小 IO 单位 | 一页就是一次 IO 的成本单位，树高即页访问次数（见 [[MySQL索引为什么用B+树]]） |
| 区 extent | 64 个连续页 = **1MB** | 按区分配空间，范围扫描与预读才有连续 IO |
| 段 segment | **每个索引两个段**：叶子节点段 + 非叶节点段 | 叶子页物理连续，范围扫描顺序读；段先逐页长出前 32 页，之后按整区申请，大段一次最多加 4 个区 |
| 表空间 tablespace | 逻辑容器：系统表空间、独立表空间（每表一个 .ibd）、undo、临时表空间 | 独立表空间才能单表回收空间，`innodb_file_per_table` 默认开 |

> [!note] 页大小可以改，但要一开始就定
> `innodb_page_size` 支持 4KB / 8KB / 16KB / 32KB / 64KB，只能在初始化实例时定死，之后全实例统一。页小则 IO 次数多，页大则一次搬运的数据多，16KB 是默认的折中。

行格式默认 `DYNAMIC`：超长的 VARCHAR / BLOB 不整段塞进叶子页，而是溢出到溢出页，行内只留一个 20 字节指针——所以大字段不会把 B+ 树的扇出撑塌。

## 双写缓冲：WAL 兜不住的那一种崩

redo 能救「已提交但页还在内存」的改动，但救不了**页写了一半**：16KB 的页刷盘途中断电或被强杀，数据文件里留下的是撕开的半页。redo 是页级物理日志，重放的前提是页本身完好，页坏了它也无从下手。双写缓冲把「写一页」拆成两步：

```chain
刷脏页 | 从 buffer pool 取出待刷的页 | 起点
写双写区 | 连续大块写 + 一次 fsync | 保险
写真实位置 | 各表空间里的随机位置 | 落地
恢复校验 | 页损坏就用双写区副本覆盖 | 兜底
```

> [!note] 写两遍不等于两倍开销
> 官方口径：第一遍进双写区是**大块顺序写**、只发一次 `fsync()`，只有第二遍才是原来那些随机写，代价远小于字面上的两倍 IO。

8.0.20 起双写区有独立文件（`#ib_16384_0.dblwr` 这一族），此前寄生在系统表空间里；`innodb_doublewrite` 默认开启，8.0.30 起还支持 `DETECT_ONLY`（只检测不恢复，给 RAID 等自带页校验的场景）。

> [!tip] 与 redo 的分工
> redo 管「已提交、页还没刷」；双写管「页正在刷、刷到一半」。两者合起来，脏页才敢放心交给后台慢慢刷。

## 落地：ACID 对应到哪个部件

至此 MySQL 卷合上：InnoDB 的每个部件都在为一条 ACID 承诺站岗。

| 承诺 | 谁负责 | 展开 |
|---|---|---|
| 原子性 | undo log 反向回滚 | [[MySQL 日志]] |
| 持久性 | redo log（WAL）+ 双写缓冲 | [[MySQL 日志]]、本篇 |
| 隔离性 | 行锁 / Next-Key Lock + MVCC 版本链 | [[MySQL 事务隔离级别]]、[[MVCC]] |
| 一致性 | 上述三者的合力，外加约束与外键 | — |

调优上真正值得动手的只有三处：

| 旋钮 | 何时动 |
|---|---|
| `innodb_buffer_pool_size` | 几乎总是第一优先：先让热数据装进内存，再谈别的 |
| `innodb_old_blocks_pct` | 大表扫描频繁、热页被冲 |
| `innodb_adaptive_hash_index` / `innodb_change_buffering` | 高并发争用或批量写场景，压测对比后再定 |

<details>
<summary>面试问答 (5题)</summary>

Q：InnoDB 和 MyISAM 有什么区别？

A：四点：事务（InnoDB 支持 ACID，MyISAM 完全不支持）；锁粒度（行锁 vs 表锁）；外键（InnoDB 支持）；崩溃恢复（InnoDB 靠 redo 重放 + undo 回滚，MyISAM 崩溃后表可能损坏只能 repair）。此外索引实现不同：InnoDB 是聚簇索引，叶子存整行，二级索引叶子存主键；MyISAM 是非聚簇，叶子存行的物理地址。这也是 5.5 起默认引擎换成 InnoDB 的原因。

Q：InnoDB 的内存结构有哪些？

A：四块：Buffer Pool 缓存数据页与索引页，所有读写都在这里发生；Change Buffer 缓冲非唯一二级索引的改动，等页读入时再合并；Adaptive Hash Index 为频繁等值访问的页自动建内存哈希；Log Buffer 是 redo 落盘前的中转站。

Q：Buffer Pool 的 LRU 和教科书 LRU 有什么区别，为什么？

A：教科书 LRU 把新页插链表头，全表扫描会把只读一次的页灌满整个池、冲掉热页。InnoDB 改成中点插入：链表分 young（约 5/8）与 old（约 3/8）两段，新页插在分界点；old 段的页要距首次访问超过 innodb_old_blocks_time（默认 1000ms）再被访问，才晋升到 young 头部。扫描页在毫秒内被连续访问也不晋升，最后从 old 尾部淘汰。

Q：Change Buffer 是什么，为什么唯一索引用不了？

A：非唯一二级索引的写改动，在目标索引页不在 Buffer Pool 时先记进内存中的 Change Buffer，等页被读入时合并，把随机读推迟掉。唯一索引写入必须立刻读页判重，页无论如何都要读，缓冲没有意义——所以写多读少的表用普通索引更划算。

Q：有 redo log 为什么还需要双写缓冲？

A：redo 是页级物理日志，重放前提是页本身完好；而 16KB 的页写到一半崩溃会留下撕裂的半页，redo 补不了。双写缓冲让刷脏时先把页顺序写进独立的双写区（一次 fsync），再写到真实位置；恢复时发现页损坏就用双写区的副本覆盖。它管的是 redo 管不到的那一类崩溃。

</details>

<details>
<summary>常见误区 (5条)</summary>

- 误区：Buffer Pool 缓存的是行。缓存单位是页（16KB），行只是页里的记录，改一行会让整页变脏。
- 误区：新读入的页放在 LRU 头部。插在中点（old 段头部），并把首次访问后 1 秒内的重复访问当作没看见，防的就是全表扫描把热页冲走。
- 误区：有了 redo log 就不怕任何崩溃。redo 重放基于完好的页；页写一半的撕裂只能靠双写缓冲。
- 误区：InnoDB 的 COUNT(*) 和 MyISAM 一样快（或一样慢）。MyISAM 读表头计数直接返回；InnoDB 因各事务可见行集不同必须扫描，走最小的二级索引。
- 误区：change buffer 对所有索引生效。只对非唯一二级索引，且目标页不在 Buffer Pool 时才缓冲；含降序索引列的索引也不支持。

</details>
