# InnoDB

:::lede
InnoDB 是 MySQL 的事务型存储引擎：支持 ACID 事务、行级锁与 MVCC，负责数据在内存与磁盘上的组织、并发控制与崩溃恢复，是 MySQL 默认引擎。
**边界：** 引擎层只管存取 · 解析、优化、连接与 binlog 归 Server 层
:::

改一行数据不去碰磁盘上的那一行，而是在内存里改它所在的 16KB 页，改动以顺序日志落盘（WAL——见 [[MySQL 日志]]）。「随机 IO 换内存操作 + 顺序写」贯穿所有部件：Buffer Pool 管内存页，表空间 → 区 → 页的分层让落盘连续，双写缓冲补上 WAL 管不到的那一种崩溃；索引长在它的页里，事务跑在它的日志与锁上。

## 引擎定位：InnoDB 与 MyISAM

MySQL 5.5 起 InnoDB 是默认引擎，8.0 起连系统表也全换成 InnoDB；问 MyISAM 是问能力边界，不是选型建议：

| 维度 | InnoDB | MyISAM |
|---|---|---|
| 事务 | ✅ ACID，靠 undo / redo 落地（见 [[MySQL 日志]]） | ❌ 无事务 |
| 锁粒度 | 行锁（默认），并发写不同行不冲突 | 表锁，一次写锁住整张表 |
| 外键 | ✅ | ❌ |
| 崩溃恢复 | ✅ redo 重放 + undo 回滚 | ❌ 表可能损坏，需 repair |
| 索引叶子存什么 | 聚簇索引存整行，二级索引存主键值 | 非聚簇，叶子存行的物理地址 |
| COUNT(*) | 必须扫描 | 表头维护行计数，无 WHERE 时直接返回 |
| 全文索引 | ✅（5.6 起） | ✅ |

InnoDB 不存行数：各事务可见的行集不同，任何固定数字必然对部分事务是错的，只能遍历最小的可用二级索引（没有二级索引才扫聚簇索引）；`COUNT(*)` 与 `COUNT(1)` 无性能差别。

## 内存结构：四个部件

只有第一块是主战场，另外三块都是它的补丁：

| 部件 | 干什么 | 一句话记忆 |
|---|---|---|
| Buffer Pool | 缓存数据页与索引页，读写都先在这里发生 | 最该调大的参数 |
| Change Buffer | 把「目标索引页不在池里」的改动先记下，等页读入时再合并 | 只服务非唯一二级索引 |
| Adaptive Hash Index | 为频繁等值访问的页自动建内存哈希，省掉 B+ 树下探 | 默认开，高并发下可能反成争用点 |
| Log Buffer | redo 落盘前的中转站 | 刷盘策略见 [[MySQL 日志]] |

磁盘侧是表空间 → 段 → 区 → 页的分层。

## Buffer Pool：读写在内存里发生

读写单位是页（默认 16KB）：读一行先把页读进池，改一行也在池里改，改完的页叫脏页、等后台刷回磁盘。

| 配置 | 默认 | 怎么定 |
|---|---|---|
| innodb_buffer_pool_size | 128MB | 专用数据库机器可到物理内存的 80%（官方原话「up to 80%」）；同 [[分库分表]]「热数据装得下就够用」 |
| innodb_buffer_pool_instances | 8（池小于 1GB 时为 1） | 大池拆成多实例，减少并发访问池元数据的争用 |

池里的页按（表空间号，页号）定位，三条链表各管一段生命周期：

| 链表 | 装什么 | 作用 |
|---|---|---|
| free | 还没用上的空闲页 | 读入新页时从这里分配 |
| LRU | 已读入、可被淘汰的页 | 池满时从冷端淘汰 |
| flush | 脏页，按变脏先后排队 | 刷盘队列，checkpoint 推进靠它（见 [[MySQL 日志]]） |

### 改进 LRU：新页为什么插在中点

标准 LRU 把新页插链表头，全表扫描会把只读一次的页灌满池、冲掉热页；InnoDB 改成中点插入：

```chain
读入新页 | 插在 young 与 old 的分界点 | 中点
短暂访问 | 时间窗内不晋升 | 防污染
反复访问 | 超时才升到 young 头部 | 真热页
淘汰 | old 尾部先出局 | 兜底
```

- 链表分 young（热端，约 5/8）与 old（冷端，约 3/8），分界比例由 `innodb_old_blocks_pct` 控制，默认 **37**（即 3/8）。
- old 段的页要**距首次访问超过 `innodb_old_blocks_time`（默认 1000 毫秒）**再被访问，才晋升到 young 头部；扫描页在毫秒内被连续访问、全落在时间窗内，晋升不了。
- 大表扫描多时官方举例把 `innodb_old_blocks_pct` 调到 5，让「读一次就不再用」的数据最多只占池子一小块。

### 预读与刷脏

- 线性预读：一个区（64 页）中顺序读到的页达到 `innodb_read_ahead_threshold`（默认 56，取值 0~64）就异步预读**下一个区**；随机预读默认关闭。
- 刷脏：8.0 由 page cleaner 线程做；脏页占比过 `innodb_max_dirty_pages_pct_lwm`（默认 10%）提前刷、到 `innodb_max_dirty_pages_pct`（默认 90%）转激进刷；自适应刷脏跟着 redo 生成速度调整，避免 redo 写满被迫强刷（sharp checkpoint）卡顿（见 [[MySQL 日志]]）。
- `innodb_flush_neighbors`：8.0 默认 0（不连带刷同区相邻页，SSD 推荐）；5.7 默认 1。

## Change Buffer：推迟二级索引的随机读

改一行要连带改每个二级索引，而这些索引页多半不在池里，为此把页读进来，一次插入就成了好几次随机读。Change Buffer 先把改动记在内存里，等页因别的原因被读进池时再合并（merge）：

| 项 | 内容 |
|---|---|
| 适用对象 | **非唯一二级索引**的 INSERT / UPDATE / DELETE 改动 |
| 生效前提 | 目标索引页不在 Buffer Pool 中 |
| 存在形式 | 内存里占 Buffer Pool 的一部分，落盘在系统表空间；改动同样记 redo，宕机不丢 |
| 合并时机 | 页被读入时、主线程空闲时、慢关闭时 |
| 上限 | `innodb_change_buffer_max_size` 默认 25（占池子百分比，最大 50） |

> [!note] 唯一索引为什么用不上
> 唯一索引写入必须**立刻**读页判重，页既然已经被读进来了，缓冲也就无从谈起——这正是「写多读少的表用普通索引更划算」的机理，选型对比见 [[MySQL 索引]]。含降序索引列的二级索引同样不支持缓冲。

合并的账迟早要还：受影响的二级索引多、改动量大时 merge 可能持续**数小时**，提交后继续、甚至跨重启——缓冲只是把随机读推迟，不是消灭它。

## 自适应哈希索引：给热页抄近路

B+ 树查一行要 3~4 次页访问；某个索引页的等值查找特别频繁时，InnoDB 自动用索引键的前缀在内存里为它建一份哈希，下次一次定位。

- 「自适应」= 建与删都由 InnoDB 自己判断，只能整体开关：`innodb_adaptive_hash_index` 默认 ON，按 `innodb_adaptive_hash_index_parts`（默认 8，最大 512）分片减少争用。
- 只服务等值与直接定位；范围扫描、`LIKE '%x%'` 这类用不上。
- 它也可能反过来成为瓶颈：并发 join 这类重负载下访问哈希索引会变成争用源，开不开靠压测对比；`SHOW ENGINE INNODB STATUS` 的 SEMAPHORES 段见 `btr0sea.c` 的 rw-latch 等待，就调大分片数或关掉。

## 磁盘结构：从表空间到页

层层套娃，每一层都为同一个目的——让 IO 尽量连续：

| 层 | 单位 / 内容 | 为什么这么分 |
|---|---|---|
| 页 page | **16KB**，InnoDB 最小 IO 单位 | 一页就是一次 IO 的成本单位，树高即页访问次数（见 [[MySQL 索引]]） |
| 区 extent | 64 个连续页 = **1MB** | 按区分配空间，范围扫描与预读才有连续 IO |
| 段 segment | **每个索引两个段**：叶子节点段 + 非叶节点段 | 叶子页物理连续，范围扫描顺序读 |
| 表空间 tablespace | 逻辑容器：系统表空间、独立表空间（每表一个 .ibd）、undo、临时表空间 | 独立表空间才能单表回收空间，`innodb_file_per_table` 默认开 |

`innodb_page_size` 只接受 4 / 8 / 16 / 32 / 64KB 五档，只能初始化实例时定死、全实例统一；16KB 是默认折中。行格式默认 `DYNAMIC`：超长 VARCHAR / BLOB 溢出到溢出页，行内只留 20 字节指针，不会把 B+ 树的扇出撑塌。

## 双写缓冲：WAL 兜不住的那一种崩

redo 能救「已提交但页还在内存」的改动，救不了**页写了一半**：16KB 页刷盘途中断电会留下撕开的半页，而 redo 是页级物理日志、重放的前提是页本身完好。双写把「写一页」拆成两步：

```chain
刷脏页 | 从 buffer pool 取出待刷的页 | 起点
写双写区 | 连续大块写 + 一次 fsync | 保险
写真实位置 | 各表空间里的随机位置 | 落地
恢复校验 | 页损坏就用双写区副本覆盖 | 兜底
```

> [!note] 写两遍不等于两倍开销
> 第一遍进双写区是**大块顺序写**、只发一次 `fsync()`，只有第二遍才是原来那些随机写。

8.0.20 起双写区有独立文件（`#ib_16384_0.dblwr` 这一族），此前寄生在系统表空间里；`innodb_doublewrite` 默认开启，8.0.30 起还支持 `DETECT_ONLY`（只检测不恢复，给 RAID 等自带页校验的场景）。

## 落地：ACID 对应到哪个部件

InnoDB 的每个部件都在为一条 ACID 承诺站岗：

| 承诺 | 谁负责 | 展开 |
|---|---|---|
| 原子性 | undo log 反向回滚 | [[MySQL 日志]] |
| 持久性 | redo log（WAL）+ 双写缓冲 | [[MySQL 日志]]、本篇 |
| 隔离性 | 行锁 / Next-Key Lock + MVCC 版本链 | [[MySQL 事务隔离级别]]、[[MVCC]] |
| 一致性 | 上述三者的合力，外加约束与外键 | — |

<summary>面试问答 (2题)</summary>

Q：Change Buffer 是什么，为什么唯一索引用不了？

A：非唯一二级索引的写改动，在目标索引页不在池里时先记进内存，等页读入时合并，把随机读推迟掉。唯一索引必须立刻读页判重，页反正要读，缓冲没有意义。

Q：有 redo log 为什么还需要双写缓冲？

A：redo 是页级物理日志，重放的前提是页本身完好；页写一半崩溃会留下撕裂的半页，redo 补不了。双写缓冲把页先顺序写进双写区（一次 fsync）再写真实位置，恢复时用副本覆盖损坏页。

</details>

<details>
<summary>常见误区 (2条)</summary>

- 误区：Buffer Pool 缓存的是行。缓存单位是页（16KB），行只是页里的记录，改一行会让整页变脏。
- 误区：InnoDB 的 COUNT(*) 和 MyISAM 一样快（或一样慢）。MyISAM 读表头计数直接返回；InnoDB 因各事务可见行集不同必须扫描，走最小的二级索引。

</details>
