# UDP

:::lede
UDP（User Datagram Protocol，用户数据报协议）是传输层无连接的数据报协议：在 IP 之上只增加端口多路复用与差错检测，不保证交付、顺序与不重复。
**分界：** 无连接 · 尽最大努力交付 · 可靠与拥塞控制交给应用层
:::

UDP 是传输层无连接的「尽力交付」协议：8 字节固定首部、无握手无重传，以数据报为单位收发；在 IP 之上只提供「多路复用 + 差错检测」，可靠、顺序、拥塞全交给应用层。

它适合实时与查询类低延迟场景，与 [[TCP]] 互补而非劣化版，同属 [[计算机网络]] 传输层。

## 协议定位与对比

| 维度 | UDP | TCP |
|---|---|---|
| 连接 | 无连接 | 面向连接（握手建连） |
| 可靠性 | 尽力交付，不保证到达 / 不重 / 有序 | 不丢、不重、按序 |
| 数据有序性 | 不保证，乱序到达需应用层排序 | 严格按序交付 |
| 传输单位 | 数据报（保留消息边界） | 字节流（无边界） |
| 全双工 | 支持对称收发，但无连接状态 | 面向连接的全双工 |
| 流量 / 拥塞控制 | 无 | 有 |
| 首部开销 | 8 字节固定 | 20 字节起 |
| 校验和 | 标准强制（现代实现默认开启）；IPv4 可置 0，IPv6 强制 | 必选（覆盖伪首部） |
| 广播 / 多播 | 支持 | 不支持 |
| 适用场景 | 实时音视频、DNS、游戏 | 文件、网页、邮件 |

## 首部格式

UDP 首部固定 8 字节，无变长选项：

| 字段 | 字节 | 作用 |
|---|---|---|
| 源端口 | 2 | 可选，不需回包可置 0 |
| 目的端口 | 2 | 必填，接收方多路复用依据 |
| 长度 | 2 | 首部 + 数据总长，最小 8；**不表示 IP 层总长度** |
| 校验和 | 2 | 校验失败直接丢弃 |

## 核心特点

| 特点 | 含义 | 影响 |
|---|---|---|
| 无连接 | 发前不握手、无连接状态 | 单包独立、延迟最低 |
| 尽力交付 | 不保证到达 / 不重 / 有序 | 无重传、无确认，丢包静默 |
| 数据报边界 | send 一次 ≈ recv 一次 | 按消息收发，不像 TCP 要自己拆流 |
| 无拥塞控制 | 发送速率不随网络状况收敛 | 网络拥塞时可能批量丢包，需应用层限速 |
| 无状态 | 服务端无需保存每连接上下文 | 易做高并发，但也易成反射放大源 |

## 校验和

- 覆盖 **伪首部 + UDP 首部 + 数据**：伪首部含源 / 目的 IP、协议号（17）、UDP 长度，只参与计算、不上网，用来防错投到错误主机 / 端口。
- 检测到差错直接丢弃，不通知发送方（无重传机制）；IPv4 允许置 0，IPv6 为 0 则收端丢弃。

## 工程陷阱

| 陷阱 | 后果 | 工程应对 |
|---|---|---|
| IP 分片 | 任一分片丢失整包作废；中间设备易丢大包 | 单包控制在 < MTU（常用 1400B），或自研分片 |
| 接收缓冲区满 | 无流量控制，新包直接丢弃 | 加大 `rmem`、应用层 ACK 反馈、限速 |
| 反射放大攻击 | 小请求大响应 → 被利用做 DDoS | 源 IP 限速、请求验证、QUIC Retry / Cookie |
| sendto 成功 ≠ 送达 | 仅进入内核发送队列 | 应用层回包确认或 QUIC 化 |

> [!danger] 接收缓冲区截断
> `recvfrom` 缓冲区小于数据报长度时，**剩余字节被内核静默丢弃**（Linux / macOS 不报错）；缓冲区建议 ≥ 65535，或用 `MSG_TRUNC` 探测。

## 适用场景

| 场景 | 选 UDP 的原因 |
|---|---|
| 实时音视频 / 通话 | 偶发丢包 < 重传等待，宁可丢帧保流畅 |
| DNS / DHCP / SNMP | 单请求单响应、报文 < 512 字节，免握手延迟低；超 512 字节或区域传送回落 TCP |
| 多人在线游戏 | 高频小包、可容忍少量丢；关键帧重传 + 非关键帧丢弃 + FEC |
| 广播 / 多播 | TCP 仅点对点，UDP 天然支持一对多 |
| QUIC / HTTP3 / RTP | 在 UDP 之上自建可靠 / 加密 / 多路复用，见 [[HTTP]] |
| VPN / 隧道（WireGuard / IPSec） | 承载加密隧道，规避 TCP 头阻塞，性能优于 TCP 隧道 |

- QUIC 把 [[TCP]] 的可靠 / 拥塞 / TLS 搬进用户态跑在 [[UDP]] 上，规避内核协议栈改造成本，是 HTTP/3 的承载层（见 [[HTTP]] / [[HTTPS]]）。

<details>
<summary>面试问答 (3题)</summary>

Q：UDP 如何实现可靠传输？

A：UDP 本身不保证，需可靠时由应用层自建序列号、确认、重传与超时（如 QUIC、RTP+RTCP）。

Q：UDP 有粘包问题吗？

A：没有。UDP 保留数据报边界，`recvfrom` 一次取到完整一个数据报；「粘包」是 TCP 字节流无边界引发的。

Q：UDP Client 一直高速发包，Server 处理不过来会怎样？

A：没有流量控制 / 背压，内核接收缓冲区（`rmem`）满后新包被**直接丢弃**，Client 无感——除非应用层有 ACK 反馈或限速。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：UDP 不可靠 = 没用。实时音视频、DNS、游戏要低延迟，丢一两包优于等重传。
- 误区：UDP 校验和保证可靠。它只检测差错并丢弃，不重传、不通知。
- 误区：UDP 一定比 TCP 快。小数据省握手确实快，但要自己重写可靠 + 拥塞控制，未必比 TCP 高效。

</details>
