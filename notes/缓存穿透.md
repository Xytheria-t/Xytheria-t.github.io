# 缓存穿透

## 思维链路速查

```chain
现象定义 | key 根本不存在 | 区分
成因与危害 | 每次都打 DB | 核心
解法全景 | 四层防御体系 | 策略
三场景对比 | 见 MOC | 关联
面试问答 | 高频考点 | 复盘
```

穿透 = 查询的 key 在缓存和 DB 中都不存在，缓存无法命中、也无法回填有效值，每次请求都穿透到 DB。它与 [[缓存雪崩]]、[[缓存击穿]] 同属缓存引发的典型异常，差异只在「失效范围」：雪崩是一片、击穿是单点、穿透是无此物。

## 现象定义

| 概念 | 触发 | 受影响范围 | 根因 |
|---|---|---|---|
| 缓存穿透 | 查不存在的 key | 单点 | key 本身不存在，无缓存可命中 |
| 缓存击穿 | 单个热点 key 失效 | 单点 | 热点 key 失效 + 高并发重建 |
| 缓存雪崩 | 大量 key 同时过期 / 宕机 | 大面积 | 过期集中或缓存层不可用 |

> [!important] 心法
> 穿透的本质是「查一个永远 miss 的 key」。解法不是优化缓存命中，而是「要么提前知道它没有，要么别让请求到达 DB」。

> [!note] 边界：冷启动不是穿透
> 冷数据首查 miss 后从 DB 回填（Cache-Aside），仅一次查询、回填即命中 → 属预热缺失。穿透是 key 在 DB 也不存在，无法回填、反复落 DB。

## 成因与危害

```chain
恶意/id 错误 | 非法参数或爬虫 | 刷不存在 id
缓存无此键 | 永不命中 | 每查必落 DB
DB 也无 | 无值可回填 | 资源被无意义消耗
```

| 成因 | 典型场景 | 危害 |
|---|---|---|
| 业务异常参数 | 错误 id / 越权查询 | 无意义 DB 查询激增 |
| 恶意爬虫 / 攻击 | 随机不存在 key 扫库 | DB 被打满 |

## 解法全景

```chain
入口拦截 | 校验+限流 | 防恶意
前置过滤 | 布隆过滤器 | 挡大部分
事后兜底 | 空值缓存 | 补误判
终极熔断 | DB 限流降级 | 防打死
```

| 层级 | 方案 | 做法 | 防什么 | 代价 |
|---|---|---|---|---|
| 第一层（入口拦截） | 参数校验 + 限流 | 格式/范围/权限拦截 + 单 IP 频次限制 | 非法请求与恶意扫库到达 DB | 业务侵入、误伤正常用户 |
| 第二层（前置过滤） | 布隆过滤器 | 所有合法 key 预置 bitmap，不存在直接拒绝 | 绝大多数不存在 key 落 DB（零 DB 开销） | 需维护、有误判（删不了） |
| 第三层（事后兜底） | 空值缓存 | 查不到也写 `null` + 短 TTL | 布隆误判与漏网请求重复查 DB | 短暂内存浪费、可能缓存穿透窗口 |
| 第四层（终极熔断） | DB 限流/降级 | resilience4j / Hystrix 兜底 | DB 被打死 | 需引入熔断组件 |

> [!tip] 布隆过滤器还是空值缓存？
> 布隆过滤器在「入口」拦截，零 DB 查询，但需预置且有误判（说存在不一定存在）；空值缓存在「查完之后」兜底，实现简单但每次首次仍落 DB。生产常两者叠加：布隆挡大部分，空值兜底误判与边界。

```chain
布隆过滤器 | 说「没有」直接返回 | 拦截
查缓存 | 布隆说「有」才查 | 未命中
查 DB | 缓存 miss 回源 | 也为空
写空值 | null + 短 TTL | 兜底
```

四层按「入口 → 缓存 → DB → 空值兜底」的顺序层层递进，前一层拦不住的才落到下一层。

> [!info] 布隆过滤器怎么维护（面试官常追问）
> - 定期全量重建：每天凌晨跑 Job 重建 Bitmap（最简单、工业级常见）。
> - RedisBloom 模块：支持动态扩容，免手动重建。
> - 替代结构：布谷鸟过滤器（Cuckoo Filter）支持删除。
> - 误判影响：误判只会让个别本不存在的 key 穿透到 DB，由空值缓存兜底——布隆 + 空值是黄金搭档，不必过度担心误判。

> [!warning] 空值缓存的坑
> 空值 TTL 要短（如 1~5min），否则大量不存在 key 长期占用内存；且必须序列化为特殊占位符（如 `"NULL"`），避免和业务正常空字符串混淆。
> 进阶：按 key 动态性设 TTL——恶意随机 ID（如 `userId=-1`）TTL 极短（30s）并限频；业务边界值（如未上架商品 ID）TTL 稍长（10min）。

## 三场景对比

| 异常 | 治的是 | 核心手段 | 详见 |
|---|---|---|---|
| [[缓存穿透]] | 无此物（key 不存在） | 布隆过滤器 / 空值缓存 | 本篇 |
| [[缓存击穿]] | 一点（单热点失效） | 互斥重建 / 逻辑过期 | 查的 key 存在，只是刚过期 |
| [[缓存雪崩]] | 一片（集中失效 / 宕机） | 错峰 TTL / 多级缓存 / 熔断 | 失效范围最大 |

> [!note] 一眼区分
> 三者的差异只在**失效范围**：穿透是「压根没这个东西」，击穿是「一个热点没了」，雪崩是「一整片同时没了」。穿透加分布式锁是典型错配——查不存在的 key 根本没有可合并的回源。

<details>
<summary>面试问答 (4题)</summary>

Q：缓存穿透怎么解决？

A：布隆过滤器在入口拦截不存在的 key；查不到也缓存空值并设短 TTL 兜底；再加接口参数校验与限流。三者常叠加。

Q：布隆过滤器有什么缺点？

A：有误判率（说存在不一定真存在，说不存在一定不存在），且不支持删除。需要定期重建或用布谷鸟过滤器支持删除。

Q：空值缓存会不会撑爆内存？

A：会，如果大量不存在 key 都缓存 null。所以空值 TTL 要短，且生产优先用布隆过滤器在入口拦截，空值只兜底层。

Q：怎么区分是穿透攻击还是正常业务？

A：监控 DB 的 qps 与缓存命中率。若大量查询的 key 具备「随机性」（UUID 或自增 ID 跳跃）且 DB 返回空结果集比例飙升，基本可判定为穿透攻击，需触发布隆过滤器重建或加 IP 黑名单。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：穿透 = 击穿，都加锁。穿透查的是「无此物」，锁无用；加分布式锁不仅无效，锁竞争反而加剧 DB 压力，纯属负优化。要靠过滤 / 空值。
- 误区：布隆过滤器万能。有误判、不支持删除，需配合空值兜底。
- 误区：不缓存 null。不缓存会导致每次穿透落 DB，必须缓存空值或在入口拦截。

</details>
