# JVM 垃圾回收

:::lede
GC（垃圾回收）是 JVM 自动识别并回收「不再可达」对象所占堆内存的机制：判活依据是可达性分析，从 GC Roots 出发走不到的对象即为可回收。
**边界：** 只管堆上对象何时可安全回收 · 不等同于立即释放 · 内存怎么划分见 [[JVM 运行时数据区]]
:::

## 思维链路速查

```chain
判活 | 谁算垃圾 | 根基
回收算法 | 清除 · 复制 · 整理 | 手段
收集器演进 | 吞吐 → 低延迟 | 落地
调优与排障 | 日志 · 症状 | 收尾
面试问答 | 高频考点 | 复盘
```

回收只回答两件事：谁该死（判活），以及怎么收才不拖垮用户线程（算法与收集器）。

## 判活：谁算垃圾

| 判活方案 | 原理 | 缺陷 | 采用方 |
|---|---|---|---|
| 引用计数 | 被引用 +1、断开 -1，为 0 即回收 | 循环引用永不归零；不能移动对象 | Python / COM 计数打底；[[JVM]] 不用，理由见 [[引用计数]] |
| 可达性分析 | 从 GC Roots 出发，不可达即垃圾 | 标记有成本，起点要 STW | HotSpot 及主流 JVM |

JVM 弃用引用计数的完整理由（写屏障计数税、不能移动对象）见 [[引用计数]]。

GC Roots：

| 根 | 说明 |
|---|---|
| 虚拟机栈引用 | 各线程栈帧局部变量表正在用到的对象 |
| 静态变量 | 类的 static 字段 |
| 常量引用 | 运行时常量池里的引用 |
| JNI 引用 | native 代码持有的对象 |
| 其他 | 持锁对象、JMXBean、类加载器等 |

四种引用强度，决定何时才轮到它被回收：

| 引用 | 语义 | 回收时机 | 典型用途 |
|---|---|---|---|
| 强引用 | 普通赋值 `Object o = x` | 只要可达就永不回收 | 绝大多数业务代码 |
| 软引用 SoftReference | 内存不足才让路 | 抛 OOM 前回收 | 内存敏感缓存 |
| 弱引用 WeakReference | 活到下次 GC 为止 | 一旦 GC 立即回收 | `ThreadLocalMap` 的 key、WeakHashMap |
| 虚引用 PhantomReference | 形同虚设，只管通知 | 随时可回收 | 堆外内存回收的 Cleaner 信号 |

> [!note] 不可达 ≠ 立即死
> 不可达对象先被标记一次；重写 `finalize()` 且未被调用过的进 F-Queue 自救（重新挂回引用链），第二次标记才真回收。`finalize()` 自 JDK 9 废弃，清理逻辑别挂它上面。

> [!tip] ThreadLocal 泄漏的根因
> `ThreadLocalMap.Entry` 的 key 是弱引用（保证 ThreadLocal 本体可回收），value 却是强引用——线程活着、Entry 不被清理，value 就永远可达。弱引用救不了 value，`remove()` 才是正解。

## 回收算法

| 算法 | 流程 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| 标记-清除 | 标记存活 → 直接清除死对象 | 简单，对象多死快时高效 | 内存碎片；效率随对象量下降 | CMS 老年代 |
| 标记-复制 | 存活者复制到另一半空间 | 无碎片，指针碰撞分配快 | 空间浪费一半；存活多则复制贵 | 新生代（朝生夕死） |
| 标记-整理 | 标记存活 → 向一端移动 | 无碎片，不浪费空间 | 移动对象要停顿更新引用 | 老年代 |

> [!warning] 算法选择由分代假设决定
> 「绝大多数对象朝生夕死」→ 新生代用复制，存活者少、复制便宜；「老对象大概率继续活」→ 老年代用标记-清除或标记-整理，复制 90% 存活对象不划算。分代布局见 [[JVM 运行时数据区]]。

## 对象晋升与跨代引用

| 机制 | 说明 |
|---|---|
| 晋升阈值 | 熬过 `MaxTenuringThreshold`（默认 15）次 Minor GC 仍存活 → 移入老年代 |
| 动态年龄判断 | Survivor 中同龄对象之和超一半时，该年龄及以上整体晋升，不必等满 15 |
| 大对象直入 | 超阈值对象免复制直接进老年代；G1 里是 Humongous Region |
| 分配担保 | Minor GC 前评估老年代连续空间，不足即担保失败，退化成 Full GC |
| 卡表 + 写屏障 | 老年代按 ~512B 分卡，引用赋值处写屏障标脏；Minor GC 只扫脏卡找跨代引用 |
| 记忆集 RSet | G1 每个 Region 维护「谁引用了我」，回收前按 RSet 反查，不必扫全堆 |

「Minor GC 不关心老年代」是错的：老年代可能持有新生代引用，卡表只标脏卡，就是为了不做全堆遍历。

## 并发标记与三色标记

| 颜色 | 含义 |
|---|---|
| 白 | 尚未访问，结束时仍白 → 回收 |
| 灰 | 自身已标，成员引用还没扫完 |
| 黑 | 自身与成员都已扫完，确认存活 |

并发期间改引用有两类漏标：**新增引用**（黑→白）与**删除引用**（灰→白断开）。修复思路：

| 方案 | 手段 | 代价 | 采用者 |
|---|---|---|---|
| 增量更新 | 黑新增指向白时，把黑记下来重扫 | 重新标记阶段 STW 更长 | CMS |
| 原始快照 SATB | 并发开始时拍快照，期间被删的白按快照存活 | 产生浮动垃圾，宁可留到下一轮也不漏标 | G1 |

## 收集器演进

| 收集器 | 作用区 | 算法 | 目标 | 状态 |
|---|---|---|---|---|
| Serial | 新生代 | 复制 | 单线程，简单高效 | 客户端 / 小内存 |
| ParNew | 新生代 | 复制 | Serial 的多线程版 | 配 CMS 的搭档 |
| Parallel Scavenge | 新生代 | 复制 | 吞吐量优先 | JDK 8 默认（配 Parallel Old） |
| Serial Old | 老年代 | 标记-整理 | 单线程 | CMS 失败后备 |
| Parallel Old | 老年代 | 标记-整理 | 吞吐量优先 | JDK 8 默认组合 |
| CMS | 老年代 | 标记-清除 | 最短停顿 | JDK 9 弃用，14 移除 |
| G1 | 全堆 | Region 化；整体标记-整理、局部复制 | 可预测停顿 | JDK 9+ 默认 |
| ZGC | 全堆 | 着色指针 + 读屏障 | 停顿 <1ms，TB 级堆 | 15 转正；21 分代（JEP 439）、23 默认（JEP 474）、24 移除非分代（JEP 490） |
| Shenandoah | 全堆 | 转发指针 + 读屏障，并发整理 | 停顿与堆大小无关 | 15 转正（JEP 379）；分代 24 引入、25 转正（默认单代） |

```chain
Serial | 单线程 STW | 起点
Parallel | 多线程换吞吐 | JDK 8 默认
CMS | 并发标记换低停顿 | 先驱
G1 | Region 分治 · 可预测停顿 | 现役默认
ZGC | 读屏障 · 停顿亚毫秒 | 大堆未来
```

### CMS：为低停顿付出的代价

四阶段：初始标记（STW，只标 Roots 直连）→ 并发标记 → 重新标记（STW，增量更新修正）→ 并发清除。

- 并发失败：并发阶段用户线程还在分配，老年代预留不足即 `Concurrent Mode Failure`，退化成 Serial Old 单线程整理，停顿反而远超平时；`-XX:CMSInitiatingOccupancyFraction` 调的就是多早开始回收。
- 碎片：不移动对象，碎片攒到放不下大对象就提前 Full GC——JDK 9 起被 G1 取代的直接原因。

### G1：Region 分治

| 机制 | 说明 |
|---|---|
| Region | 堆切成 2048 个左右等大 Region；Eden / Survivor / Old / Humongous 只是角色标签，不是物理连续区 |
| Humongous | ≥ Region 一半的对象独占连续 Region，直接进老年代区 |
| 回收价值优先 | 优先回收垃圾占比高、回收收益大的 Region（Garbage First 之名由此） |
| 停顿预测模型 | `-XX:MaxGCPauseMillis=200`，据此决定每轮收集多少 Region |

调优入口只有一个：只设 `-Xms` / `-Xmx` 与 `MaxGCPauseMillis`，其余交给自适应模型。

## 调优与排障

GC 日志（JDK 9+ 统一日志）：

```bash
java -Xms4g -Xmx4g -XX:+UseG1GC -Xlog:gc*,gc+heap=debug:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20m -jar app.jar
```

| 症状 | 首查方向 |
|---|---|
| Minor GC 频繁且晋升量大 | 新生代偏小 / 对象过早晋升，看 Survivor 使用率与年龄分布 |
| Full GC 频繁 | 老年代泄漏（`jmap -histo` / MAT 支配树）或元空间涨（动态类生成） |
| 单次 Full GC 特别长 | 老年代过大上的整理停顿，考虑 G1 / ZGC 分而治之 |
| `Concurrent Mode Failure` | CMS 预留不足，调低触发阈值或换 G1 |
| 停顿尖刺与负载相关 | `Safepoint` 偏头（大对象遍历、计数循环），开 `-Xlog:safepoint` 看 |

选型：吞吐优先（批处理）→ Parallel；停顿可控（在线服务）→ G1；超大堆 + 亚毫秒延迟 → ZGC。

<details>
<summary>面试问答 (4题)</summary>

Q：如何判断对象可以被回收？

A：可达性分析——从 GC Roots 出发，引用链不可达的对象可回收；引用计数因循环引用不被 JVM 采用。

Q：Minor GC、Major GC、Full GC 的区别？

A：Minor GC 只收新生代，频繁且快；Major GC 通常指老年代收集；Full GC 收整堆 + 方法区，最慢。

Q：CMS 和 G1 的区别？

A：CMS 标记-清除，有碎片与并发失败风险；G1 把堆切成 Region 按回收价值优先收集，有停顿预测模型、无碎片，JDK 9 起是默认。

Q：什么是三色标记？漏标怎么解决？

A：白未扫、灰扫到一半、黑扫完。漏标源于「黑新增指向白」或「灰到白的引用被删」；CMS 用增量更新（重扫黑），G1 用 SATB（按快照保活，产生浮动垃圾）。

</details>

<summary>常见误区 (3条)</summary>

- 误区：Full GC 频繁就该加大堆。泄漏场景堆越大死得越慢，先 `jmap` / MAT 找支配树里的泄漏源。
- 误区：JVM 不用引用计数只是因为循环引用。环只是导火索，真正的账是写屏障计数税 + 不能移动对象，见 [[引用计数]]。
- 误区：CMS 被 G1 取代是因为停顿不够低。主因是碎片 + 并发失败退化，G1 用 Region 分治一起解决。

</details>
