# 类加载器

:::lede
类加载器（ClassLoader）是 JVM 中负责把类字节码读入内存、生成对应 `Class` 对象的组件：它定位 `.class` 来源、读取字节流，再交给 JVM 定义成类型。它只决定「类从哪来、由谁定义」，不负责加载之后的链接与初始化。
:::

## 思维链路速查

```chain
四层加载器 | 分层职责与加载范围 | 全景
命名空间 | 类的唯一性判据 | 核心
数组类 | 不由加载器创建 | 边界
自定义加载器 | 覆写 findClass 的实践 | 落地
面试问答 | 高频考点 | 复盘
```

四个加载器各管一块地盘，而「加载器 + 全限定名」才是类的真正身份；数组类是这条规则的豁免项，自定义加载器则把规则变成可编程的能力。

## 四层加载器

| 加载器 | 实现 | 加载范围 | `getParent()` |
|---|---|---|---|
| Bootstrap | C++ 实现，不是 Java 对象 | JDK8 `rt.jar`（`jre/lib`）→ JDK9+ `lib/modules` 运行时镜像 | `null` |
| Platform（JDK8: Extension） | Java；JDK8 `sun.misc.Launcher$ExtClassLoader`，JDK9+ `ClassLoaders$PlatformClassLoader` | JDK8 `lib/ext` → JDK9+ 平台模块（`java.sql` 等） | Bootstrap（`null`） |
| Application（System） | Java；JDK8 `sun.misc.Launcher$AppClassLoader`，JDK9+ `ClassLoaders$AppClassLoader` | classpath（JDK9+ 含模块路径） | Platform |
| 自定义 | 继承 `ClassLoader` | 网络、加密字节码、热部署目录等任意来源 | Application |

继承结构：JDK 8 用 `URLClassLoader` 体系，JDK 9+ 收进 `jdk.internal.loader.ClassLoaders`。

> [!warning] Bootstrap 不是 Java 对象
> `String.class.getClassLoader()` 返回 `null`，不是「没有加载器」，而是它由 C++ 实现、不在 Java 堆里；`getParent()` 的结果要先判 null。

```java
System.out.println(String.class.getClassLoader()); // null（Bootstrap）
System.out.println(LoaderDemo.class.getClassLoader()); // JDK 8: sun.misc.Launcher$AppClassLoader；JDK 9+: jdk.internal.loader.ClassLoaders$AppClassLoader
System.out.println(LoaderDemo.class.getClassLoader().getParent()); // JDK 8: sun.misc.Launcher$ExtClassLoader；JDK 9+: ClassLoaders$PlatformClassLoader
```

## 命名空间

> [!danger] 唯一性 = 加载器 + 全限定名
> 同一个全限定名被两个加载器加载，得到**两个互不兼容的类型**：`equals` 与 `isAssignableFrom` 为 false，`instanceof` 为 false，互转抛 `ClassCastException`。

| 判据 | 说明 |
|---|---|
| `Class.getClassLoader()` | 决定该类属于哪个命名空间 |
| 父加载器可见子？ | **不可见**，父看不到子加载的类（[[双亲委派模型]] 单向委派的副作用） |
| 子加载器可见父？ | **可见**，子能沿委派链拿到父加载的类 |

隔离的工程样本是 Tomcat 的 `WebAppClassLoader`，见 [[破坏双亲委派]]。

## 数组类

数组类**不由类加载器创建**：JVM 运行时直接构造，没有对应的 `.class` 文件，也走不到加载流程。

| 数组类型 | 归属的加载器 |
|---|---|
| `User[]`（元素是引用类型） | 元素类型的加载器，即 `User.class.getClassLoader()` |
| `int[]`（元素是基本类型） | `null`（等同 Bootstrap） |

`new User[10]` 只构造数组对象，**不触发**元素类初始化（被动引用，见 [[类加载过程]]）。

## 自定义加载器

```java
public class DiskClassLoader extends ClassLoader {
    private final Path dir;
    public DiskClassLoader(Path dir) { this.dir = dir; }

    @Override   // 只重写 findClass：定义「去哪取字节码」，委派留在 loadClass
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            byte[] bytes = Files.readAllBytes(dir.resolve(name.replace('.', '/') + ".class"));
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}
```

| 方法 | 是否重写 | 作用 |
|---|---|---|
| `findClass` | **是** | 定义「去哪取字节码」，保留委派 |
| `defineClass` | 否 | 字节数组 → `Class` 的落点；protected，由 `findClass` 调用 |
| `loadClass` | 否 | 委派主流程；重写即绕过模型（刻意[[破坏双亲委派]]时除外） |

<details>
<summary>面试问答 (2题)</summary>

Q：如何判断两个类是否「同一个类」？

A：全限定名相同**且**由同一个类加载器加载，二者缺一不可。

Q：`getParent()` 返回 null 意味着什么？

A：两种可能：父加载器是 Bootstrap（如 Platform 的父），或自己就是 Bootstrap、根本没有 Java 对象。

</details>

<details>
<summary>常见误区 (2条)</summary>

- 误区：`ExtClassLoader` 在 JDK 9 后仍是「扩展」加载器。已改名 Platform，加载平台模块而非 `lib/ext`。
- 误区：加载器之间可互相访问。只有子能看见父（沿委派链），反向不行。

</details>
