# RAG

## 思维链路速查

```chain
离线索引 | 文档到向量库 | 建库
在线检索 | 改写、召回、重排 | 取数
拼装生成 | 上下文与引用 | 生成
评测与演进 | 指标与进阶形态 | 复盘
```

大模型的参数是冻结的知识，RAG 不去改参数，而是在每次回答前把相关材料检索出来塞进上下文——所以整条链路的成败几乎都由检索质量决定：该召回的块没进上下文，生成模型再强也答不对。

## 为什么需要 RAG

| 方案 | 知识更新 | 成本 | 可控性 | 适合 |
|---|---|---|---|---|
| 微调 | 要重训 | 高（数据 + 算力） | 弱，知识揉进参数、难溯源 | 风格、格式、领域语感 |
| RAG | 改索引即可 | 低（检索 + 少量 token） | 强，可给引用、可删数据 | 私有知识、频繁更新的事实问答 |
| 长上下文硬塞 | 每次重传 | 高（token 随文档线性增长） | 中，易被无关内容干扰 | 小规模、一次性文档 |

> [!note] 边界澄清
> RAG 治的是「知识不在模型里」，治不了「推理能力不足」：模型本身推不出的题，检索再多材料也答不对。二者常叠加——微调定风格，RAG 供事实。

## 离线索引链路

```chain
解析清洗 | 去模板、去页眉页脚 | 入口
分块 | 按语义边界切 | 关键
向量化 | embedding 模型编码 | 编码
入库 | 向量 + 元数据 | 落库
```

分块是这条链路里最容易被忽视、又最影响效果的一步：块太大噪声多、token 贵；太小语义断裂、上下文缺失。

| 策略 | 做法 | 适用 |
|---|---|---|
| 递归切分 | 按「段落 → 换行 → 句号 → 空格」优先级切，带重叠（如 800 字 / 重叠 150） | 通用首选，中文分隔符要补 `。` |
| 语义切分 | 在 embedding 相似度突变处断句 | 结构松散的长文档 |
| 父子块 | 小块用于检索，命中后回填父块给模型 | 需要完整上下文的问答 |
| 结构化切分 | 按标题层级、表格、代码块切 | 手册、API 文档、法规 |

- **元数据是检索的一半**：来源、章节、时间、权限标签随块一起入库，检索时才能过滤（权限、时效）并生成引用。
- **增量索引**：文档更新按 `doc_id` 覆盖重写，别全量重建；删除要真删，向量库与缓存都要同步。

> [!warning] 重叠不是万能
> 重叠缓解边界断裂，但会让同一句话出现在多个块里，检索后必须去重（按内容哈希或按父块聚合），否则上下文被同一段话塞满。

## 在线检索链路

```chain
查询改写 | 补全指代、扩展多查询 | 入口
混合召回 | 向量 + BM25 各取一批 | 粗筛
融合重排 | RRF 合并 + 交叉编码器 | 精排
上下文组装 | 去重、裁剪、排序 | 交给模型
```

- **查询改写**：多轮对话里的「它」要补全成实体；再扩展成多条查询（multi-query）或先生成假想答案再检索（HyDE）以提高召回。简单问题不必改写——改错比不改更糟。
- **混合召回**：稠密向量擅长语义相近（同义改写也能召回），稀疏 BM25 擅长术语、型号、编号的精确命中，两路各取一批（如各 20 条）再用 RRF（倒数排名融合）合并；ES 里就是 `dense_vector` kNN 与 BM25 双路，见 [[倒排索引]]。
- **重排**：交叉编码器把「查询 + 候选块」拼在一起打分，精度远高于向量点积，但只能跑小候选集（如 20 → 5）。
- **上下文组装**：去重、按相关性排序、按 token 预算裁剪；关键证据放开头或结尾——模型对中间位置的内容注意力最弱（lost in the middle）。

| 阶段 | 目标 | 典型量级 |
|---|---|---|
| 召回 | 别漏（高 recall） | 数十到上百条 |
| 重排 | 别错（高 precision） | 收敛到 3~10 条 |
| 生成 | 别编（有依据） | 上下文不超预算 |

## 生成与引用约束

- **提示词约束**：「只依据上下文回答，上下文没有就说不知道」——缺这条，模型会用参数里的旧知识补答案。
- **引用溯源**：返回块级引用（文档 + 章节），既方便核验，也让评测能对齐「答案是否真有出处」。
- **温度调低**：事实问答用 `temperature=0` 附近，减少自由发挥。
- **无答案兜底**：检索得分低于阈值时直接回「未找到」，比硬生成一段看似合理的答案更安全。

## 落地：最小可跑链路

```python
# 索引：递归切分 → 向量化 → 入库
splitter = RecursiveCharacterTextSplitter(
    chunk_size=800, chunk_overlap=150,
    separators=["\n\n", "\n", "。", ". ", " ", ""],
)
chunks = splitter.split_documents(docs)
store.add(chunks)

# 检索：粗召回 20 条 → 交叉编码器重排到 5 条
cands = store.search(q, k=20)
hits = rerank(q, cands, top_n=5)   # 交叉编码器：query 与候选块拼接后打分

# 生成：只依据上下文，找不到就直说
prompt = ("仅根据以下上下文回答；上下文没有答案就回答「我没有足够的信息」。\n"
          f"{fmt(hits)}\n问题：{q}")
answer = llm(prompt, temperature=0)
```

## 评测

| 环节 | 指标 | 怎么算 |
|---|---|---|
| 检索 | Recall@k | 标注的「应召回块」有多少进了 top-k |
| 检索 | MRR / NDCG | 首个正确结果的名次 / 整体排序质量 |
| 生成 | 忠实度 | 答案里的断言能否被检索上下文支持 |
| 生成 | 答案相关性 | 答案是否真正回答了问题 |
| 检索 | 上下文精度 | 召回块里有用块的比例 |

- 起步只要一份带标注的问题集（几十条真实问题即可），把评测挂进 CI，改 prompt、换模型前后对比。
- 没有生成侧标注时，最低成本做法是先标「问题 → 应召回块 ID」，只盯检索侧指标，把召回稳住。

> [!tip] 先修检索，再修生成
> 检索漏了，换更强的生成模型也救不回来；检索对了而答案仍错，才轮到调 prompt 与模型。

## 进阶形态

| 形态 | 思路 | 解决什么 |
|---|---|---|
| 混合检索 + RRF | 稠密与稀疏融合 | 术语漏召、语义漏召 |
| HyDE / 多查询 | 生成假想答案或多条改写再检索 | 问题太短、表述与文档不匹配 |
| 父子块 / 句窗口 | 小块检索、大块喂模型 | 上下文被切碎 |
| GraphRAG | 抽实体关系建图，按社区摘要检索 | 跨文档、多跳、全局性问题 |
| RAPTOR | 递归聚类生成摘要树，多层检索 | 长文档的宏观问题 |
| Agentic RAG | 由 agent 决定检索几次、检索什么、是否重试 | 多跳问题与不确定查询 |
| 上下文检索 | 索引前用模型给每块补上下文说明 | 块脱离原文后语义不明 |

> [!note] 别一上来就上图
> GraphRAG、Agentic RAG 的构建与推理成本都远高于朴素 RAG；先把分块、混合检索、重排、评测做扎实，指标卡住了再上更重的形态。Agentic RAG 的检索与写操作通常也交给 [[MCP]] 暴露成工具，宿主与模型不必各自适配。

## 工程细节

- **语义缓存**：常见问题与答案（或查询向量）缓存，命中即返回，省掉整条链路。
- **延迟拆解**：改写（一次 LLM 调用）→ 召回（毫秒级）→ 重排（几十到几百毫秒）→ 生成（流式）。首字延迟主要由改写与检索决定，别把串行 LLM 调用堆在检索前面。
- **权限与多租户**：过滤必须在**检索时**按元数据完成，不能检索完再筛——否则越权内容已经进了上下文。
- **幂等与版本**：文档带版本号，重索引按版本覆盖，避免重复块累积污染召回。

<summary>面试问答 (5题)</summary>

Q：RAG 和微调怎么选？

A：知识型、更新频繁、要求可溯源选 RAG；风格、格式、领域语感且知识稳定选微调。生产上常叠加：微调定风格，RAG 供事实。

Q：为什么纯向量检索不够？

A：向量擅长语义相近，但对精确术语、型号、编号不敏感；纯关键词又不认同义改写。所以生产上普遍是稠密 + 稀疏混合召回，再用重排收敛。

Q：分块大小怎么定？

A：先按文档结构切（标题、段落、表格），再以 500~1000 字、重叠 10%~20% 起步；用评测集对比不同块长的 Recall@k，别凭感觉拍。

Q：RAG 会幻觉吗？

A：会。检索为空或相关度低时模型仍可能硬答，所以要有无答案兜底、引用约束与忠实度评测，不能假设「有上下文就一定不编」。

Q：RAG 系统怎么评测？

A：分两层：检索侧看 Recall@k、MRR、NDCG；生成侧看忠实度、答案相关性、上下文精度。用带标注的问题集挂进 CI，改动前后对比。

<details>
<summary>常见误区 (4条)</summary>

- 误区：检索结果堆得越多越准。实际噪声与 token 成本同增，还会触发 lost in the middle，需要重排收敛。
- 误区：检索完再做权限过滤。实际越权内容已进上下文，过滤必须在检索时按元数据完成。
- 误区：块切得越小召回越准。实际小块易丢上下文、语义断裂，需要父子块或重叠兜底。
- 误区：换个更大的模型就能修好答不对的问题。实际检索没召回对的证据时，生成模型无解。

</details>
