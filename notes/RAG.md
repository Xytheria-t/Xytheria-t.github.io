# RAG

:::lede
RAG（Retrieval-Augmented Generation，检索增强生成）是一种不改模型参数、在每次生成前先检索外部知识并注入上下文的生成方案，解决模型参数里没有或已过时的私有知识。
:::

## 思维链路速查

```chain
离线索引 | 文档到向量库 | 建库
在线检索 | 改写、召回、重排 | 取数
拼装生成 | 上下文与引用 | 生成
评测与演进 | 指标与进阶形态 | 复盘
```

大模型的参数是冻结知识，RAG 不改参数，而是在每次回答前把相关材料检索进上下文——成败几乎由检索质量决定：该召回的块没进上下文，生成模型再强也答不对。

## 为什么需要 RAG

| 方案 | 知识更新 | 成本 | 可控性 | 适合 |
|---|---|---|---|---|
| 微调 | 要重训 | 高（数据 + 算力） | 弱，知识揉进参数、难溯源 | 风格、格式、领域语感 |
| RAG | 改索引即可 | 低（检索 + 少量 token） | 强，可给引用、可删数据 | 私有知识、频繁更新的事实问答 |
| 长上下文硬塞 | 每次重传 | 高（token 随文档线性增长） | 中，易被无关内容干扰 | 小规模、一次性文档 |

> [!note] 边界澄清
> RAG 治「知识不在模型里」，治不了「推理能力不足」；生产上常叠加——微调定风格，RAG 供事实。

## 离线索引链路

```chain
解析清洗 | 去模板、去页眉页脚 | 入口
分块 | 按语义边界切 | 关键
向量化 | embedding 模型编码 | 编码
入库 | 向量 + 元数据 | 落库
```

分块最影响效果：块太大噪声多、token 贵；太小语义断裂、上下文缺失。

| 策略 | 做法 | 适用 |
|---|---|---|
| 递归切分 | 按「段落 → 换行 → 句号 → 空格」优先级切，带重叠（如 800 字 / 重叠 150） | 通用首选，中文要补 `。` |
| 语义切分 | 在 embedding 相似度突变处断句 | 结构松散的长文档 |
| 父子块 | 小块检索，命中后回填父块 | 需要完整上下文的问答 |
| 结构化切分 | 按标题层级、表格、代码块切 | 手册、API 文档、法规 |

- **元数据是检索的一半**：来源、章节、时间、权限标签随块入库，供检索时过滤与生成引用。
- **增量索引**：文档更新按 `doc_id` 覆盖重写，别全量重建；删除要真删，向量库与缓存同步。

> [!warning] 重叠不是万能
> 同一句话会落进多个块，检索后必须去重（按内容哈希或父块聚合）。

## 在线检索链路

```chain
查询改写 | 补全指代、扩展多查询 | 入口
混合召回 | 向量 + BM25 各取一批 | 粗筛
融合重排 | RRF 合并 + 交叉编码器 | 精排
上下文组装 | 去重、裁剪、排序 | 交给模型
```

- **查询改写**：多轮里的「它」补全成实体，扩成多条查询（multi-query）或先生成假想答案再检索（HyDE）；简单问题别改写。
- **混合召回**：稠密向量管语义相近（同义改写也能召回），稀疏 BM25 管术语、型号、编号的精确命中，两路各取一批（如各 20 条）用 RRF（倒数排名融合）合并；ES 里是 `dense_vector` kNN + BM25，见 [[倒排索引]]。
- **重排**：交叉编码器把「查询 + 候选块」拼接打分，精度远高于向量点积，但只能跑小候选集（如 20 → 5）。
- **上下文组装**：去重、按相关性排序、按 token 预算裁剪；关键证据放开头或结尾——模型对中间位置注意力最弱（lost in the middle）。

| 阶段 | 目标 | 典型量级 |
|---|---|---|
| 召回 | 别漏（高 recall） | 数十到上百条 |
| 重排 | 别错（高 precision） | 收敛到 3~10 条 |
| 生成 | 别编（有依据） | 上下文不超预算 |

## 生成与引用约束

- **提示词约束**：「只依据上下文回答，没有就说不知道」——缺这条，模型会用参数里的旧知识补答案。
- **引用溯源**：返回块级引用（文档 + 章节），便于核验与评测对齐。
- **温度与兜底**：事实问答用 `temperature=0` 附近；检索得分低于阈值直接回「未找到」，比硬编答案安全。

## 落地：最小可跑链路

```python
# 索引：递归切分 → 向量化 → 入库
splitter = RecursiveCharacterTextSplitter(
    chunk_size=800, chunk_overlap=150,
    separators=["\n\n", "\n", "。", ". ", " ", ""],
)
store.add(splitter.split_documents(docs))

# 检索：粗召回 20 条 → 交叉编码器重排到 5 条
hits = rerank(q, store.search(q, k=20), top_n=5)

# 生成：只依据上下文，没答案就说不知道
prompt = f"仅根据以下上下文回答，没有答案就回答「我没有足够的信息」。\n{fmt(hits)}\n问题：{q}"
answer = llm(prompt, temperature=0)
```

## 评测

| 环节 | 指标 | 怎么算 |
|---|---|---|
| 检索 | Recall@k | 应召回块有多少进了 top-k |
| 检索 | MRR / NDCG | 首个正确结果的名次 / 整体排序质量 |
| 生成 | 忠实度 | 答案里的断言能否被检索上下文支持 |
| 生成 | 答案相关性 | 答案是否真正回答了问题 |
| 检索 | 上下文精度 | 召回块里有用块的比例 |

起步一份带标注的问题集（几十条真问题）挂进 CI 对比改动；没有生成侧标注就先只盯检索侧指标。

## 进阶形态

> [!note] 成本远高于朴素 RAG，别一上来就上图
> GraphRAG 建实体关系图治跨文档多跳，RAPTOR 用摘要树治长文档宏观问题，Agentic RAG 由 agent 决定检索几次治不确定查询，上下文检索在索引前给每块补说明；先把分块、混合检索、重排、评测做扎实。Agentic RAG 的检索与写操作通常交给 [[MCP]] 暴露成工具。

## 工程细节

- **语义缓存**：常见问题与答案（或查询向量）缓存，命中即返回，省掉整条链路。
- **延迟拆解**：改写（一次 LLM 调用）→ 召回（毫秒级）→ 重排（几十到几百毫秒）→ 生成（流式）；首字延迟由改写与检索决定。
- **权限与多租户**：过滤必须在**检索时**按元数据完成，不能检索完再筛——否则越权内容已进上下文。
- **幂等与版本**：文档带版本号，重索引按版本覆盖，避免重复块累积污染召回。

<summary>面试问答 (4题)</summary>

Q：RAG 和微调怎么选？

A：知识更新频繁、要溯源选 RAG；风格语感且知识稳定选微调；生产常叠加。

Q：为什么纯向量检索不够？

A：向量不认精确术语、型号、编号，纯关键词又不认同义改写，所以要混合召回 + 重排。

Q：分块大小怎么定？

A：先按文档结构切，再以 500~1000 字、重叠 10%~20% 起步，用 Recall@k 对比。

Q：RAG 会幻觉吗？

A：会。检索为空或相关度低时模型仍可能硬答，要有无答案兜底与引用约束。

<details>
<summary>常见误区 (3条)</summary>

- 误区：检索结果堆得越多越准。实际噪声与 token 成本同增，还会触发 lost in the middle，需重排收敛。
- 误区：块切得越小召回越准。实际小块易丢上下文、语义断裂，需父子块或重叠兜底。
- 误区：换个更大的模型就能修好答不对的问题。实际检索没召回对的证据，生成模型无解。
