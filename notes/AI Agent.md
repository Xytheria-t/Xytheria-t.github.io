# AI Agent

AI Agent（智能体）是以大模型为决策核心、能调用工具并根据执行结果在环境中循环行动的系统，解决单次调用无法完成的开放式任务；它与 workflow 的分界是路径由模型动态决定还是代码预编排。

## 思维链路速查

```chain
Agent 是什么 | 定义与 loop | 概念
工具与行动 | 调用如何闭环 | 核心
规划与记忆 | 多步与状态 | 约束
workflow 还是 agent | 选型与边界 | 落地
面试问答 | 高频考点 | 复盘
```

agent 不是更强的模型，而是「模型在循环里」——每轮拿上一轮的观察决定下一步动作；换来自主性，代价是延迟、成本与逐轮累积的错误。

## Agent 是什么

判断一个系统算不算 agent，Anthropic 的判据只有一条：流程是代码写死的（workflow）还是模型动态决定的（agent）。

| 维度 | 单次调用 | Workflow | Agent |
|---|---|---|---|
| 路径 | 一次出结果 | 代码预编排 | 模型自选 |
| 轮数 | 1 | 固定 | 不定 |
| 成本与延迟 | 最低 | 中 | 最高 |
| 适用 | 一次能答完 | 步骤可预测 | 步骤不可预测 |

基础构件是**增强型 LLM**：在模型上叠加 retrieval、tools、memory 三类能力，由模型自己决定何时用哪个。检索怎么做到 [[RAG]]，工具怎么接进来 [[MCP]]，能力怎么打包 [[AI Agent Skill]]。

```chain
接收目标 | 用户指令进消息历史 | 入口
模型决策 | 输出回复或 tool_call | 推理
宿主执行 | 真正跑工具、拿结果 | 行动
回灌观察 | 结果作为新消息入列 | 反馈
终止判定 | 完成或达上限 | 退出
```

> [!note] 模型不执行任何东西
> 模型只输出「调哪个工具、参数是什么」，执行发生在宿主进程。工具的定义与执行面归 [[MCP]]，本篇只讲 loop。

## 工具调用怎么闭环

| 环节 | 谁做 | 产物 |
|---|---|---|
| 声明 | 开发者 | 工具 JSON Schema（名称、参数、描述） |
| 选择 | 模型 | `tool_call`（工具名 + 参数） |
| 执行 | 宿主 | 字符串或 JSON 结果 |
| 回灌 | 宿主 | 一条 `role=tool` 消息 |
| 续跑 | 模型 | 下一轮决策或最终答案 |

- 工具按 **ACI（agent-计算机接口）** 对待：描述写清用途、示例、边界与相邻工具的分工，参数名按「给新同事写 docstring」的标准取。
- 工具不是越多越好：候选挤占上下文，近义工具会选错；一个动作一个工具，交集靠描述拉开。
- 失败要回可行动的信息：「错在哪 + 怎么改」而不是抛栈，模型下一轮才有修正的抓手。

## 规划与记忆

**ReAct** = 推理（Reason）与行动（Act）交错：每轮先想一步再动手，用工具结果校正下一步，比「先一口气列完计划」更抗偏离。

| 模式 | 做法 | 适合 |
|---|---|---|
| ReAct | 想一步做一步，边做边改 | 步骤不可预测、要试错 |
| Plan-and-execute | 先出完整计划再逐步执行 | 长任务、计划需人审 |
| 反思 | 执行后自评再迭代 | 有明确评判标准 |

记忆分两层：

- **短期**：消息历史本身，受上下文窗口硬约束；超窗要压缩（摘要旧轮次、工具结果只留结构化字段）。
- **长期**：外部存储（文件、向量库、数据库），需要时检索回上下文——[[RAG]] 在 agent 里的位置。

> [!warning] 长上下文不等于记忆
> 塞满历史只是把噪声也塞进来：中间位置注意力最弱，关键证据反被挤掉。真正要做的是「选什么进上下文」——按相关性与时间裁剪、必要时改写压缩。

## workflow 还是 agent

先问能不能更简单：一次调用能解决就别上 workflow，workflow 能解决就别上 agent。

| Workflow 模式 | 做法 | 适用 |
|---|---|---|
| 提示链 | 上一步输出喂下一步，中间可加检查 | 能干净拆成固定子任务 |
| 路由 | 先分类再分流到专用流程 | 类别分明、可分别优化 |
| 并行化 | 分片并行或多次投票 | 提速 / 提高置信度 |
| 编排者-工作者 | 中心模型动态拆解并委派 | 子任务数不可预知 |
| 评估者-优化者 | 生成与评估循环迭代 | 有清晰评判标准 |

> [!tip] 选型一句话
> 开放式、步数不可预测（修 bug、跨文件改动、多源调研）才上 agent；其余优先用固定路径换可预测性。

## 落地：最小 agent 循环

```python
msgs = [{"role": "user", "content": goal}]
for _ in range(MAX_STEPS):                 # 必须设上限，防空转烧钱
    msg = llm(msgs, tools=TOOLS)
    msgs.append(msg)
    if not msg.tool_calls:
        return msg.content                 # 不再要工具 → 任务完成
    for call in msg.tool_calls:
        out = run(call.name, call.args)    # 宿主执行，异常转成文本回灌
        msgs.append({"role": "tool", "tool_call_id": call.id, "content": out})
```

- 每轮都是完整上下文重发，token 随轮数线性增长；能跑多少轮由压缩与裁剪决定。
- 高风险动作（删文件、下单、发消息）走白名单或人工确认，别让 loop 直接触达。

## 失败与护栏

- **错误累积**：一步错会带偏后续所有步，靠工具结果这一「ground truth」纠偏，并在关键节点设检查点。
- **停不下来**：设最大轮数、token 预算、超时；同一工具同一参数反复调用是典型空转信号。
- **沙箱**：代码执行与文件操作放容器或受限目录，最小权限。
- **可观测**：记录每轮输入、决策与工具结果，否则失败无法复盘——这份日志也是评测数据的源头。

<details>
<summary>面试问答 (4题)</summary>

Q：Agent 和 workflow 的区别？

A：路径谁定——workflow 由代码预编排，agent 由模型在循环里动态决定；后者更灵活，也更贵更易错。

Q：工具调用是模型在跑代码吗？

A：不是。模型只产出工具名与参数，宿主执行后把结果作为新消息回灌，再进下一轮。

Q：为什么 agent 必须设最大轮数？

A：没有终止条件会空转烧 token，且错误逐轮累积；轮数、预算、超时是最基本的护栏。

Q：agent 的记忆怎么分？

A：短期 = 上下文里的消息历史（受窗口约束，需压缩裁剪），长期 = 外部存储按需检索回上下文，见 [[RAG]]。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：上下文越长 agent 越强。实际中间位置注意力弱，噪声挤掉关键证据，裁剪比堆砌重要。
- 误区：工具列得越全越好。实际候选占上下文，近义工具易选错，一个动作一个工具。
- 误区：agent 是更强的模型。实际是同一模型多跑几轮，靠工具反馈换准确率，代价是延迟与成本。

</details>
