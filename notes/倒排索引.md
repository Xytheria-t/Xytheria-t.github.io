# 倒排索引

:::lede
倒排索引（inverted index）是全文检索用的索引结构：以词项为键、以出现该词项的文档列表（含位置信息）为值，与「文档 → 词项」的正排索引方向相反。
**组成：** 词项字典 + 倒排列表（postings list）
:::

## 思维链路速查

```chain
正排与倒排 | 谁找谁 | 概念
倒排结构 | 词典 + 倒排表 | 结构
写入链路 | 段与近实时 | 机制
查询链路 | 两阶段与打分 | 机制
分片与翻页 | 路由与深分页 | 推论
```

检索要回答的是「哪些文档含这个词」，而正排表只记「这篇文档有哪些词」——ES 把关系倒过来存，才有了毫秒级检索；代价是段不可变、写入只能追加。本篇先立倒排结构，再沿写入与查询两条链路各走一遍，最后落到分片与深分页这两个真会踩的坑。

## 正排与倒排

| 维度 | 正排（forward） | 倒排（inverted） |
|---|---|---|
| 映射方向 | 文档 → 词项 | 词项 → 文档列表 |
| 存储形式 | doc_values 列存 | 词典 + 倒排表（postings） |
| 服务场景 | 排序、聚合、取字段值 | 全文检索、term 过滤 |
| 是否分词 | 存原值 | 按分词结果建表 |

倒排不是 ES 的专利：Lucene 是它的实现内核，ES 只把它分片、包装成分布式服务；InnoDB 的 FULLTEXT 也是倒排，但没有分段、近实时与分布式分片。

## 倒排结构

倒排索引 = 词典 + 倒排表：

- **词典（term dictionary）**：词项有序存放，查找走 **FST**（有限状态转换器）——公共前缀压成有向图，省空间又能按前缀定位。
- **倒排表（postings list）**：该词项出现的文档 ID（升序），附带词频与位置；位置只服务短语查询。
- **压缩**：docID 升序 → 差值编码（delta）后按组定长存；过滤结果用位图，多条件直接位运算求交。

| 查询类型 | 依赖的结构 | 需要位置 |
|---|---|---|
| term / 布尔过滤 | 倒排表 docID | 否 |
| phrase 短语 | 倒排表 + 位置 | 是 |
| 前缀 / 通配 | FST 前缀遍历 | 否 |
| 排序 / 聚合 | doc_values 正排 | 否 |

> [!tip] 为什么 term 比 wildcard 快
> term 在词典直接命中；wildcard / regexp 要遍历词典逐个匹配，候选越多越慢——`abc*` 还能借 FST 走前缀路径，`*abc` 只能全词典扫。

## 写入链路

```chain
写内存 buffer | 同时记 translog | 入口
refresh | 生成新 segment，可搜 | 默认 1s
translog fsync | 保证重启不丢 | durability
flush | 落盘 + commit point | 段清理
merge | 段合并，真删旧文档 | 后台
```

- **buffer → segment**：文档先进索引缓冲，`refresh` 把它刷成新的 **segment**（不可变的小索引）并打开搜索，默认 `refresh_interval` 1s——这就是**近实时（NRT）**，写完要等 refresh 才搜得到。
- **translog**：写请求同时顺序写 translog；`index.translog.durability` 默认 `request`（每请求 fsync），`async` 则按 `sync_interval`（默认 5s）批量落盘——「写入不丢」靠 translog 而非 segment。
- **flush**：把段 fsync 到磁盘并写 commit point，随后清空 translog。
- **merge**：后台把小段并成大段；删除与更新只打删除标记（`.liv`），合并时才物理清除——更新 = 标记旧文档删除 + 写新文档，段会膨胀，靠 merge 回收。

## 查询链路

一次搜索分两阶段：**query phase** 在每个分片上本地打分、各取 top（`from+size`），协调节点归并出全局 top；**fetch phase** 再按文档 ID 回分片取 `_source`。

| 上下文 | 是否打分 | 是否缓存 | 典型写法 |
|---|---|---|---|
| query context | 是（BM25） | 否 | `match`、`multi_match` |
| filter context | 否 | 是（节点级 filter 缓存，段粒度位图） | `term`、`range`、`bool.filter` |

- **打分**：ES 5.0 起默认 BM25（`k1=1.2`、`b=0.75`）——词频按饱和曲线增益（避免堆词刷分），再用文档长度归一化（长文档天然词多，要折算）。
- **该过滤就别打分**：条件放进 `bool.filter` 既复用缓存、又减少参与打分的文档数；该 filter 的写成 must 是白算分。
- **只取必要字段**：排序与聚合不需要原文时用 `_source: false` + `docvalue_fields`，减少 fetch 阶段开销；调优顺序是先查白算分、再看翻页深度、最后才动分片与副本。

## 分片与深分页

- **路由**：`shard = hash(routing) % number_of_shards`，routing 默认取文档 `_id`；同一 routing 必落同一分片，所以按业务键（如 `user_id`）设 routing 能把相关数据聚到一处。
- **主分片数创建后不可改**：改分片数会打乱路由公式，只能 `reindex` / `shrink` / `split`；副本数随时可改（7.0 起新建索引默认 1 主 1 副）。
- **每个分片是一个完整 Lucene 索引**：段、缓存、打分都在分片内完成；分片过多会放大协调开销与集群状态（官方建议单分片 10~50GB）。
- **深分页**：`from + size` 要每个分片返回 `from+size` 条候选再归并，翻到第 N 页就是 O(N) 的搬运量；`max_result_window` 默认 10000 拦的正是这个。

| 方案 | 机制 | 代价 / 适用 |
|---|---|---|
| `from + size` | 各分片取 `from+size` 后归并 | 浅分页；深翻页内存与 CPU 双爆 |
| `scroll` | 快照 + 游标逐批取 | 占资源、快照不含新写入；官方已不推荐 |
| `search_after` + PIT | PIT 固定索引视图，按上一页末条的排序值续取 | 深分页首选；排序须稳定 |

> [!warning] search_after 的排序必须唯一
> 排序字段要唯一，或补一个唯一 tiebreaker（PIT 场景常用 `_shard_doc`），否则排序值相同的文档在两次请求间顺序不保证一致，翻页会漏条或重复。

## 落地：mapping 与分词

mapping 决定字段是「分词可搜」还是「精确可聚合」，写完再改就要重建索引。

- **text vs keyword**：`text` 分词后建倒排，用于全文检索；`keyword` 整串入库，用于精确匹配、排序、聚合；同一字段两种用法用 `fields` 子字段（`title.raw`）。
- **analyzer 三段**：字符过滤器 → 分词器 → 词元过滤器。中文常用 `ik_max_word`（细粒度、召回高）建索引、`ik_smart`（粗粒度）做查询；内置 `standard` 对中文按单字切，召回可以但精度差。
- **doc_values**：正排列存，默认开启，排序与聚合靠它；`text` 不存 doc_values，对 `text` 排序必须走 `keyword` 子字段（`fielddata` 默认关闭、官方不建议开）。

> [!note] 版本前提
> 随版本变的口径：7.0 起选主改 quorum 机制（不再手配 `minimum_master_nodes`）；PIT 为 7.10+、`search_after` 支持 PIT 为 7.12+；9.x（Lucene 10 内核）在倒排之上补了 `semantic_text` 与 `rank_vectors` 做语义与后期交互检索。

## 与 MySQL 的分工

| 维度 | MySQL | Elasticsearch |
|---|---|---|
| 事务 | ACID、行锁 | 无事务，仅单文档级原子性 |
| 一致性 | 强一致 | 准实时（受 refresh 延迟影响） |
| 擅长 | 点查、关联、事务写入 | 全文检索、多维过滤、聚合 |
| 数据地位 | 事实来源 | 可重建的索引副本 |

常见架构是 MySQL 存事实、ES 做检索，用 binlog + Canal（或经 MQ 解耦）异步同步，接受最终一致，分片键不含查询条件时用 ES 宽表承接跨分片检索（见 [[分库分表]]）；喂大模型时 ES 常作 [[RAG]] 的检索后端（kNN 语义召回 + BM25 关键词召回，RRF 融合）。

<details>
<summary>面试问答 (3题)</summary>

Q：ES 为什么检索快？

A：倒排把「文档 → 词」翻成「词 → 文档」，term 查询在词典直接命中倒排表；docID 升序 + 差值压缩让倒排表很小，多条件用位图求交，再靠分片并行缩短响应。

Q：为什么说是「近实时」而不是实时？

A：段不可变，新文档要等 refresh 生成新段才可搜，默认 1s；要立刻可见可写入时带 `refresh=wait_for`，代价是拖慢写入。

Q：深分页为什么慢，怎么解？

A：`from+size` 让每个分片都搬运 `from+size` 条候选，越翻越贵，`max_result_window` 默认 10000。正解是 `search_after` + PIT 按游标翻页。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：refresh 就是把数据写到磁盘。refresh 只让新段可搜，持久化靠 translog + flush。
- 误区：主分片数可以像副本一样随时改。路由公式依赖分片数，只能 reindex / shrink / split。
- 误区：拿 `text` 字段直接排序或聚合。`text` 无 doc_values，要加 `keyword` 子字段。
