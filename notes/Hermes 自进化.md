# Hermes 自进化

:::lede
**Hermes 自进化** 是 Hermes Agent 内置的学习闭环：把对话里试错得来的解法沉淀成记忆与技能，再在后续使用中持续改写这些文本制品。
**载体：** 磁盘上的记忆与技能文件
:::

## 思维链路速查

```chain
对话累积 | 轮次 / 迭代计数到阈值 | 触发
后台审查 | 影子 Agent 复盘快照 | 沉淀
落盘生效 | 记忆与技能写进磁盘 | 快循环
库房治理 | Curator 归档与合并 | 快循环
离线深挖 | GEPA 改文本 · RL 改权重 | 慢循环
```

分界线不在「会不会自己改」，而在改完之后谁来评估——快循环改的是磁盘上的文本制品，改坏了下轮还能再改；慢循环改权重，要 GPU 和人工发起。

## 三个子系统：记忆、技能、提醒

[[AI Agent]] 循环负责做事，这三个子系统负责把做过的事沉淀下来。

| 子系统 | 管什么 | 载体 |
|---|---|---|
| 记忆 | 事实与偏好 | MEMORY.md（2200 字符）· USER.md（1375 字符） |
| 技能 | 可复用的做法 | `~/.hermes/skills/<name>/SKILL.md` |
| 提醒引擎 | 何时复盘 | nudge 计数器，无独立文件 |

- 记忆是**有界**的：两个纯文本文件，会话开始时以冻结快照注入 system prompt——为保住前缀缓存，会话中途的改动要等下次会话才进 prompt。
- 记忆写满会直接报错，逼 agent 先整合（使用率超 80% 就该合并条目）；上下文压缩前还会插一次紧急提炼，优先级为偏好 > 纠正 > 模式 > 任务细节。
- 技能是**程序性记忆**：agent 用 `skill_manage` 自己建（create / patch / edit / delete），时机是「5 次以上工具调用的复杂任务成功」「试错后找到可行路径」「被用户纠正」。改法首选 `patch`——只有改动文本进上下文，比整篇 `edit` 省 token。
- 提醒引擎只是计数器：默认每 10 个用户轮次查一次记忆、每 10 次工具迭代查一次技能；agent 主动调过对应工具就把计数归零，避免重复劳动。
- 容量之外另有一条召回通道：全部会话存进 SQLite 并用 FTS5 建索引，`session_search` 按需捞原文（无 LLM 摘要）——记忆只放必须常驻的，历史留给要用再查。

> [!note] 记忆与技能的分工
> 记忆存「事实」，常驻 system prompt、有字符硬顶；技能存「做法」，按渐进披露按需加载（机制见 [[AI Agent Skill]]）。前者靠压缩控体积，后者靠归档控数量。

## 快循环：影子 Agent 的后台审查

到阈值后不打断对话，而是派生一个**影子 Agent**（daemon 线程）复盘对话快照：

- 复用主模型，`max_iterations=8`，标准输出重定向到空设备——用户事后只看到一行「已保存」摘要。
- 与主 Agent 共享同一个记忆存储（内部有文件锁），但把自身 nudge 间隔置 0，否则审查又触发审查，无限递归。
- 产出两类：写记忆条目、建或补技能；两类阈值同时到就合并成一次审查，省一次 API 调用。
- 被中断或失败的对话不审查——快照不完整，提炼出的知识会误导。

> [!tip] 两个计数器为什么不同口径
> 记忆按**用户轮次**计（偏好散布在对话时间线上），技能按**工具迭代**计（一轮里连调 8 个工具本身就是可提炼的信号）。

## Curator 的技能库治理

技能库会自己膨胀：agent 每解决一个新问题就落一份 SKILL.md，不治理很快堆出几十个范围狭窄的近似重复项，污染目录还烧 token。

| 维度 | 规则 |
|---|---|
| 触发 | 空闲检查而非 cron：距上次运行 ≥7 天，且 agent 已空闲 ≥2 小时 |
| 阶段一 | 确定性状态转换（无 LLM）：14 天未用 → `stale`，30 天未用 → 归档 |
| 阶段二 | LLM 单次审查：逐技能决定保留 / 修补 / 合并重叠项 |
| 依据 | `.usage.json` 的 use_count / view_count / patch_count |
| 底线 | 只碰 agent 自建技能；`pin` 过的免疫；**绝不删除**，最坏归档，可 `restore` |
| 回滚 | 每次运行前打 tar.gz 快照，一条命令撤销整次运行 |

## 慢循环：GEPA 与权重训练

改权重是另一条链路：导出执行轨迹配 Atropos 跑 RL，手动发起、要 GPU。

GEPA（Genetic-Pareto）则把快循环的文本优化升级成**有评估集的搜索**，是官方 self-evolution 项目（独立仓库，产出 PR 而非直改主干）的引擎：

- 采样执行轨迹（推理、工具调用、工具输出）→ **用自然语言反思失败原因** → 文本级变异出候选 → 从 Pareto 前沿组合互补经验。
- 评估集四来源：强模型合成用例（冷启动）、真实会话挖掘（LLM-as-judge 按 rubric 打分）、手写黄金集、技能专属自动评估。
- 论文在 6 个任务上平均超 GRPO 6%、最高 20%，rollout 用量最多少 35 倍；比 MIPROv2 高 10% 以上（AIME-2025 +12%）。单次成本约 $2–10，无需 GPU。

## 边界与局限

- 影子 Agent **无法评估自己产出的质量**：可能把误解沉淀成技能，而系统没有自动验证环节，纠错靠用户后续发现。
- Curator 治理的是库的**形状**（重复、陈旧、漂移），判据来自使用遥测；技能内容对不对，它没有独立的正确性信号。
- 快循环改的全是文本制品，模型能力仍是天花板：换小模型驱动，多步任务照样中途跑偏。
- 记忆的字符硬顶是设计意图而非缺陷——逼 agent 压缩，只留高价值信息。

<details>
<summary>面试问答 (4题)</summary>

Q：Hermes 自进化改的是什么？
A：改磁盘上的文本制品——记忆文件、技能文件、提示与工具描述；权重不动，改权重走导出轨迹 + RL 的另一条链路。

Q：nudge 怎么触发，为什么用两个计数器？
A：默认每 10 个用户轮次查记忆、每 10 次工具迭代查技能；偏好按轮次显现、密集工具调用按迭代显现，故口径不同。

Q：技能库膨胀怎么处理？
A：Curator 在空闲时（间隔 7 天 + 空闲 2 小时）跑两阶段：先按 14 / 30 天确定性转 stale 与归档，再让 LLM 审一遍合并重叠项；只归档不删除，可回滚。

Q：GEPA 凭什么比 RL 省？
A：它读执行轨迹用自然语言反思失败原因，把诊断直接写成文本改动；RL 只能从稀疏标量奖励里反推，常需数千次 rollout。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：自进化 = 模型自己改权重。→ 快循环全程不动权重；改权重是离线 RL，需人工发起。
- 误区：后台审查会打断对话。→ 审查跑在影子 Agent 里（daemon 线程、静默），事后只留一行摘要。
- 误区：技能越多越强。→ 无人治理的技能库会退化成几十个近似重复项，Curator 正是为修剪它而存在。

</details>
