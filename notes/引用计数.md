# 引用计数

:::lede
引用计数是一种内存管理策略：给每个对象记被引用的次数，归零即立即释放。
它判活只看计数，与可达性分析是两条路。
**缺陷：** 回收不了循环引用 · [[JVM 垃圾回收]] 主用可达性分析
:::

## 思维链路速查

```chain
机制 | 加减计数与即时回收 | 起点
死穴 | 循环引用永不归零 | 根因
代价 | 计数税 · 并发 · 不可移动 | 权衡
破环者 | Python · COM · Swift | 对照
JVM 的选择 | 可达性分析 | 结论
```

加减计数、即时回收看似干净，循环引用却让计数永远归不了零；补丁能救个别语言，结构性代价躲不掉——这正是 JVM 改选可达性分析的理由。

## 机制：计数怎么工作

| 操作 | 计数变化 | 结果 |
|---|---|---|
| `a = b` | b +1，a 的旧值 -1 | 赋值即维护 |
| 离开作用域 / 字段被覆盖 | -1 | 断开即扣减 |
| 计数归零 | 立即释放 | 回收时机确定 |
| 释放一个对象 | 它引用的每个字段 -1 | 可能触发级联释放 |

> [!tip] 引用计数的优点是真实的
> 即时回收（断开那一刻就释放，析构时机可预测）、无集中 STW、堆占用低。面试只答「循环引用」是半个答案——JVM 是算过账才放弃的。

## 死穴：循环引用

互相持有的两个对象，外部引用断开后计数仍是 1，永不归零：

```python
a = []; a.append(a); del a   # 计数 2 → 1，永不归零
```

```java
x.next = y; y.next = x; x = y = null;   // 同样的环：两者皆不可达 → 正常回收
```

环是对象图的常态：双向链表、父子互指、观察者注册、闭包捕获 `self`、模块与顶层函数互指——破环责任交还程序员，「自动内存管理」就只剩一半。

## 代价：不是「补个环检测」就完事

| 代价 | 痛点 | 对照 JVM |
|---|---|---|
| 赋值计数税 | 引用赋值最热，每次都要增减 | 平时赋值零记账 |
| 并发计数税 | 计数增减必须线程安全 | GIL 白嫖；去 GIL 得偏置计数硬扛 |
| 移动税 | 无反向信息，移动要修全堆 | 分代 · 复制 · 整理全靠能移动 |
| 头部开销 | 计数字段人人付账 | 对象头不带计数 |
| 零散释放 | 写指针即结账，成本 ∝ 写操作数 | 成本 ∝ 存活集，GC 期一次清算 |

- 计数税可削：延迟计数 / 合并计数把加减挪到 GC 期批算。
- 并发税可削：free-threaded CPython（PEP 703：3.13 实验性 → 3.14 起为受支持选项，GIL 仍默认）用偏置计数 + 不朽对象 + 延迟计数；账单是 AMD64 对象头 16B → 约 32B。
- 移动税无解：无反向引用信息、无统一引用枚举机制，复制 / 整理 / 分代全出局；tracing 的写屏障只在跨代 / 并发标记时插固定代码，平时赋值不记账。

## 破环：三种破环方案

| 采用者 | 主机制 | 谁负责破环 | 兜底 |
|---|---|---|---|
| CPython | RC 打底 + 分代 tracing（`gc` 模块只跟踪可能成环的容器对象） | 循环检测自动兜底 | 环只能等 gc 跑，不再即时回收 |
| COM | `AddRef` / `Release` 手工计数 | 程序员 | 无；漏一次 Release 就泄漏，环自己拆 |
| Swift ARC | 编译器插桩计数 | 程序员（`weak` / `unowned` 标注） | 无 tracing 兜底，标错就泄漏 |
| JVM | 可达性分析 | 无人 | 环天然被吃掉 |

> [!warning] 「Python 用引用计数」只是半句
> 真正的循环回收靠 `gc` 模块的分代 tracing 兜底：CPython 是 RC + tracing 的混合体，问题从来不是「RC 还是 tracing」，而是「要不要为即时回收付两份机制的价钱」。

## JVM 的选择

```chain
正确性零负担 | 环天然被吃 · 程序员不用想谁持强引用 | 首要
mutator 近零成本 | 平时赋值不带计数税 | 吞吐
能移动对象 | 分代 · 复制 · 整理 · Region 全可用 | 算法空间
缺点可工程化 | 并发标记 · 分代 · 读屏障压停顿 | 收尾
```

> [!tip] 一句话版
> tracing 的缺点是可以优化掉的成本（集中停顿 → 并发标记、分代、Region 压）；RC 的缺点是机制自带的税（环、计数税、不可移动），压不下去。

## Java 里还有引用计数吗

有，但只在 GC 管不到的地方：

| 场景 | 做法 | 为什么还得计数 |
|---|---|---|
| Netty `ByteBuf` | `refCnt` 手工 `retain` / `release` | 堆外内存不在堆里，tracing 扫不到 |
| `DirectByteBuffer` | `Cleaner`（虚引用）发信号触发释放 | 靠 GC 通知，不是靠计数判活 |

规律：引用计数在 Java 里只作为 GC 管辖之外的手工手段出现，堆内判活交给 [[JVM 垃圾回收]] 的可达性分析。

<details>
<summary>面试问答 (4题)</summary>

Q：JVM 为什么不用引用计数？

A：三条账——环永不归零；每次赋值都要维护计数，税摊在最高频操作上；没有反向引用信息所以不能移动对象，复制 / 整理 / 分代全废。

Q：Python 用引用计数，它怎么解决循环引用？

A：靠 `gc` 模块的分代循环检测兜底（只跟踪可能成环的容器对象），所以是 RC + tracing 混合；成环对象不再即时回收。

Q：引用计数相比可达性分析有什么优点？

A：回收时机确定（引用断开即释放）、无集中 STW、堆占用低；代价是计数税与算法工具箱被砍一半。

Q：那 Java 里还见得到引用计数吗？

A：见得到，但只在 GC 管不到的地方：Netty `ByteBuf` 的 `refCnt`、`DirectByteBuffer` 的 `Cleaner`；堆内判活走可达性分析。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：不用引用计数只是因为循环引用。环是导火索，真正的账是每次赋值的计数税 + 不能移动对象。
- 误区：引用计数没有停顿。单次释放很分散，但长引用链的根断开会引发级联 Release，可能长停顿甚至爆栈（CPython 用 trashcan 机制缓解）。
- 误区：RC 一定更省内存。计数器占对象头（free-threaded CPython 为线程安全把头从 16B 撑到约 32B），tracing 则要额外空闲堆做周转，方向不同。

</details>
