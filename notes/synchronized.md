# synchronized

## 思维链路速查

```chain
加锁范围 | 方法/块/静态 | 入口
释放与可重入 | 语义保证 | 安全
锁升级 | 偏向→轻量→重量 | 核心
编译期优化 | 消除/粗化 | 实战
面试问答 | 高频考点 | 复盘
```

synchronized 是 JVM 内置互斥锁(管程) → 加锁范围决定锁对象 → 自动释放 + 可重入 + 可见性 → 竞争加剧触发锁升级 → 编译期还有锁消除/粗化 → 面试常考升级与对比。

## 加锁范围

| 用法 | 锁对象 | 说明 |
|---|---|---|
| 实例方法 | `this`(当前实例) | 同一实例互斥 |
| 静态方法 | `Class` 对象 | 类级互斥,所有实例共享 |
| 同步块 `synchronized(obj)` | 指定对象 | 粒度最细,推荐 |

> [!warning] 锁对象选择
> 锁必须是对所有竞争线程**同一个**对象；用 `new Object()` 每次新建或锁 `String` 常量池对象都会失效。字符串字面量进运行时常量池,不同处写 `"x"` 可能是同一把锁,易踩坑——底层见 [[JVM 运行时数据区]] 的「String.intern() 与字符串驻留」。

## 释放与可重入

三条语义都由同一个结构兑现——**monitor(管程)**:JVM 给每个对象配的锁实体,内部记两个字段:**owner**(当前持锁线程)、**重入计数**(同一线程再进一次就 +1):

| 语义 | 规则 |
|---|---|
| 可重入 | 加锁时 owner 已是自己 → 计数 +1 直接进,不重新抢 |
| 自动释放 | 退出时计数 -1,**归零才清 owner、真正放锁**;正常返回、抛异常都会走到,不会锁泄漏 |
| 可见性 | 放锁前的写,对随后拿到**同一把锁**的线程可见(happens-before 监视器锁规则) |

> [!note] 没有可重入,嵌套调用就自己锁自己
> - 同步方法调本类另一个同步方法——还是同一把 `this`,自己等自己
> - 子类 `synchronized` 方法里调 `super.method()`——锁的还是同一个 `this`
>
> 可重入 = 同一线程再进同一把锁只 +1 计数,不重抢。

计数怎么走,看一段递归:

```java
class MathUtil {
    synchronized int fact(int n) {   // 每进入一层,同一把锁重入一次:计数 1→2→3→…
        return n <= 1 ? 1 : n * fact(n - 1);
    }
}
// 递归回程逐层退出:计数 -1、-1、-1…减到 0 这一刻才真正放锁
```

「自动释放」由 JVM 在字节码层兑现:一段看似三行的 Java 代码

```java
void m() {
    synchronized (this) {
        x++;
    }
}
```

编译出的字节码骨架(只留锁相关指令,`x++` 本体省略):

```text
monitorenter        ← 进入:拿 this 的 monitor,计数 0→1
   ...              ← x++ 的字段读写,与锁无关
monitorexit         ← 退出 1:正常路径,计数 1→0,放锁
goto  RETURN
monitorexit         ← 退出 2:异常路径,任何异常先跳到这
athrow              ← 放完锁,再把异常抛出去
RETURN
```

> [!note] 两个 `monitorexit` 不是冗余
> - 编译器不知道 m 会不会抛异常,正常路径、异常路径**各配一个 exit**
> - 异常表(编译器生成的异常处理器)把任意异常引到第二个 exit:先放锁、再 rethrow——「抛异常也不锁泄漏」的落地位置

> [!tip] 同步方法为什么没有这两条指令
> - 锁信息不在指令里,记在方法的访问标志 **`ACC_SYNCHRONIZED`** 上(静态方法再叠 `ACC_STATIC`)
> - JVM 调用时读 flag,隐式走「enter → 方法体 → exit」等价流程;返回/抛异常同样保证释放,与同步块底层是同一个 monitor
> - `javap -v` 一眼分辨:有 `monitorenter` = 同步块;没有但带 `ACC_SYNCHRONIZED` = 同步方法

## 锁升级（JDK 6+）

| 阶段 | 触发 | 实现 | 代价 |
|---|---|---|---|
| 无锁 | 未竞争 | — | 最低 |
| 偏向锁 | 单线程进入 | 偏向线程 ID 写入 Mark Word,省 CAS | 极低 |
| 轻量级锁 | 多线程交替 | 自旋 CAS 抢锁 | 低(自旋耗 CPU) |
| 重量级锁 | 竞争激烈 | 操作系统互斥量,线程 park 阻塞 | 高(上下文切换) |

> [!tip] 各阶段在做什么
> - **偏向**:对象头 Mark Word 里记下「这把锁归线程 X」,同一个线程再来连 CAS 都省了;一旦发现第二个线程来抢 → 升级为轻量级。
> - **轻量级**:每个线程在自己栈帧里生成「锁记录(Lock Record)」,用 **CAS** 把对象头的指针改成自己记录的指针;抢到就干活,抢不到就**自适应自旋**几下再试,不立刻 park。
> - **重量级**:自旋白烧 CPU 也拿不到,CAS 失败次数超阈值 → 把对象头指针换成指向**互斥量(mutex)**;没抢到的线程进**等待队列**被 OS 挂起,park / unpark 来回,代价高(用户态 ↔ 内核态切换)。

> [!warning] 升级不可逆 · 偏向锁已下线
> 锁只能升级不能降级(批量重偏向/撤销除外)。**偏向锁在 JDK 15 起默认禁用、JDK 18 起实质移除**,新版本 `synchronized` 直接走 轻量级→重量级;JDK 8/11 默认开启,可用 `-XX:-UseBiasedLocking` 关闭。升级路径只属于 `synchronized`,基于 [[AQS]] 的 [[ReentrantLock]] 等无此路径。

> [!note] 自适应自旋 vs 固定自旋
> 轻量级阶段的自旋**次数不写死**,由 JVM 根据上一次自旋成功率动态调:上次转几圈就拿到 = 这次多转几圈;上次转半天也拿不到 = 这次少转甚至不自旋。目的是让「短临界区」少走重量级路径,「长临界区」别白烧 CPU。

## 编译期优化

- **锁消除**：逃逸分析判定变量不逃逸出线程,自动去掉无用锁(如方法内局部 `StringBuffer`)。
- **锁粗化**：连续对同一对象加锁(如循环体内),合并为一次大锁减少开销。

<details>
<summary>面试问答 (4题)</summary>

Q：synchronized 怎么保证释放？

A：同步块编译出 `monitorenter` 与两个 `monitorexit`(正常 + 异常路径),同步方法走 `ACC_SYNCHRONIZED`;无论正常还是异常退出 JVM 都会释放,不会锁泄漏。

Q：锁升级过程？

A：无锁→偏向锁(单线程,Mark Word 记线程 ID)→轻量级锁(自旋 CAS)→重量级锁(OS 互斥量,线程 park)。只升不降;注：偏向锁在 JDK 15 后已逐步下线。

Q：synchronized 能保证可见性吗？

A：能。unlock 前的所有写,对随后 lock 同一监视器的线程可见(happens-before 监视器锁规则);但只覆盖加同一把锁的线程,不加锁的线程仍可能读到旧值。

Q：和 ReentrantLock 比？

A：synchronized 自动释放、简单、非公平、不可中断/超时；ReentrantLock 灵活但需手动 unlock。详见 [[Java 锁对比]]。

</details>

<details>
<summary>常见误区 (4条)</summary>

- 误区：synchronized 性能一定差。JDK6 锁升级后低竞争场景开销很小,多数场景与 [[ReentrantLock]] 差距可忽略。
- 误区：锁字符串安全。字面量进常量池,不同处写同一个字面量可能意外共享同一把锁(底层见 [[JVM 运行时数据区]] 的字符串驻留)。
- 误区：锁 `Integer` 等包装类没问题。`-128~127` 走缓存且 `i++` 会换新对象,锁会失效;要用专门的锁对象。
- 误区：加了 synchronized 就全局互斥。实例方法锁 `this`、静态方法锁 `Class`,两者互不阻塞;要全局互斥必须锁同一个对象。

</details>
