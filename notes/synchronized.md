# synchronized

synchronized 是 JVM 内置的互斥锁，以对象为锁单位、由 monitor（管程）兑现，加锁解锁自动完成且可重入。它没有中断、超时、公平与多条件这些能力，那些是显式锁的领地。

## 思维链路速查

```chain
加锁范围 | 方法/块/静态 | 入口
释放与可重入 | 语义保证 | 安全
锁升级 | 偏向→轻量→重量 | 核心
编译期优化 | 消除/粗化 | 实战
面试问答 | 高频考点 | 复盘
```

synchronized 是 JVM 内置互斥锁(管程) → 加锁范围决定锁对象 → 自动释放 + 可重入 + 可见性 → 竞争加剧触发锁升级 → 编译期还有锁消除/粗化 → 面试常考升级与对比。

## 加锁范围

| 用法 | 锁对象 | 说明 |
|---|---|---|
| 实例方法 | `this`(当前实例) | 同一实例互斥 |
| 静态方法 | `Class` 对象 | 类级互斥,所有实例共享 |
| 同步块 `synchronized(obj)` | 指定对象 | 粒度最细,推荐 |

> [!warning] 锁对象选择
> 锁必须是对所有竞争线程**同一个**对象:`new Object()` 每次新建会失效;`Integer` 缓存对象(`-128~127` 复用,`i++` 又换新对象)同样锁不住。字符串字面量进运行时常量池,不同处写 `"x"` 可能是同一把锁,易踩坑——底层见 [[JVM 运行时数据区]] 的「String.intern() 与字符串驻留」。

## 释放与可重入

三条语义由同一个结构兑现——**monitor(管程)**:JVM 给每个对象配的锁实体,内部记 **owner**(当前持锁线程)与**重入计数**。

| 语义 | 规则 |
|---|---|
| 可重入 | 加锁时 owner 已是自己 → 计数 +1 直接进,不重新抢 |
| 自动释放 | 退出时计数 -1,**归零才清 owner、真正放锁**;正常返回、抛异常都会走到,不会锁泄漏 |
| 可见性 | 放锁前的写,对随后拿到**同一把锁**的线程可见(happens-before 监视器锁规则,见 [[JMM]]) |

同步方法调本类另一个同步方法、子类同步方法里调 `super.method()`,锁的都是同一个 `this`——没有可重入就会自己等自己。

「自动释放」由 JVM 在字节码层兑现:

```java
void m() {
    synchronized (this) {
        x++;
    }
}
```

```text
monitorenter        ← 进入:拿 this 的 monitor,计数 0→1
   ...              ← x++ 的字段读写,与锁无关
monitorexit         ← 退出 1:正常路径,计数 1→0,放锁
goto  RETURN
monitorexit         ← 退出 2:异常路径,任何异常先跳到这
athrow              ← 放完锁,再把异常抛出去
RETURN
```

编译器不知道 m 会不会抛异常,正常、异常路径**各配一个 exit**;异常表把任意异常引到第二个 exit——先放锁再 rethrow,这就是「抛异常也不锁泄漏」的落地位置。

> [!tip] 同步方法为什么没有这两条指令
> 锁信息不在指令里,记在方法的访问标志 **`ACC_SYNCHRONIZED`** 上(静态方法再叠 `ACC_STATIC`);JVM 调用时读 flag,隐式走「enter → 方法体 → exit」等价流程,与同步块底层是同一个 monitor。`javap -v` 一眼分辨:有 `monitorenter` = 同步块;没有但带 `ACC_SYNCHRONIZED` = 同步方法。

## 锁升级（JDK 6+）

| 阶段 | 触发 | 实现 | 代价 |
|---|---|---|---|
| 无锁 | 未竞争 | — | 最低 |
| 偏向锁 | 单线程进入 | Mark Word 记偏向线程 ID,同线程再来连 CAS 都省 | 极低 |
| 轻量级锁 | 多线程交替 | 线程栈帧建锁记录(Lock Record),CAS 抢锁,失败自适应自旋 | 低(自旋耗 CPU) |
| 重量级锁 | 竞争激烈/自旋失败 | 对象头换成指向 OS 互斥量(mutex),未抢到者进等待队列 park | 高(上下文切换) |

> [!warning] 升级不可逆 · 偏向锁已下线
> 锁只能升级不能降级(批量重偏向/撤销除外)。**偏向锁在 JDK 15 起默认禁用、JDK 18 起实质移除**,新版本 `synchronized` 直接走 轻量级→重量级;JDK 8/11 默认开启。升级路径只属于 `synchronized`,基于 [[AQS]] 的 [[ReentrantLock]] 等无此路径。

## 编译期优化

- **锁消除**：逃逸分析判定变量不逃逸出线程,自动去掉无用锁(如方法内局部 `StringBuffer`)。
- **锁粗化**：连续对同一对象加锁(如循环体内),合并为一次大锁减少开销。

<details>
<summary>面试问答 (3题)</summary>

Q：锁升级过程？

A：无锁→偏向锁(单线程,Mark Word 记线程 ID)→轻量级锁(自旋 CAS)→重量级锁(OS 互斥量,线程 park)。只升不降;**偏向锁 JDK 15 起默认禁用、JDK 18 起实质移除**。

Q：synchronized 能保证可见性吗？

A：能。unlock 前的写对随后 lock 同一监视器的线程可见(happens-before 监视器锁规则);但只覆盖加同一把锁的线程,不加锁的线程仍可能读到旧值。

Q：和 ReentrantLock 比？

A：synchronized 自动释放、简单、非公平、不可中断/超时;ReentrantLock 灵活但需手动 unlock。详见 [[Java 锁对比]]。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：synchronized 性能一定差。JDK6 锁升级后低竞争场景开销很小,多数场景与 [[ReentrantLock]] 差距可忽略。
- 误区：拿字符串字面量 / `Integer` 包装类当锁安全。前者共享常量池对象,后者走 `-128~127` 缓存且 `i++` 换新对象,都可能意外互斥或锁失效(见 [[JVM 运行时数据区]])。
- 误区：加了 synchronized 就全局互斥。实例方法锁 `this`、静态方法锁 `Class`,两者互不阻塞;要全局互斥必须锁同一个对象。

</details>
