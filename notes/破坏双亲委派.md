# 破坏双亲委派

## 思维链路速查

```chain
三次破坏 | 历史兼容 SPI 动态性 | 全景
线程上下文加载器 | 父向子反向请求 | 核心
容器隔离案例 | Tomcat 与热部署 | 实战
面试问答 | 高频考点 | 复盘
```

委派链被打破过三次：为兼容旧代码、为 SPI 反向请求、为容器动态性 —— 线程上下文类加载器是其中最标准的「父借子力」通道，Tomcat 则把「先己后父」做成了工程样本。

## 三次破坏

| 次序 | 原因 | 手段 | 代表场景 |
|---|---|---|---|
| 第一次 | JDK 1.2 才把委派写进 `loadClass`，此前加载器习惯重写 `loadClass` 自己加载 | 新增 `findClass` 钩子引导新代码，旧加载器不强制迁移 | 历史遗留加载器（仍「先自己后父」） |
| 第二次 | 模型自身缺陷：**父加载器需要请求子加载器** | 线程上下文类加载器 TCCL | JDBC、JNDI、JCE、JAXB |
| 第三次 | 程序动态性：模块化多版本共存、热替换 | 重排委派顺序（Tomcat 本地优先、OSGi 按声明委派）或整体丢弃重建 | Tomcat、OSGi、JSP 热替换、Spring Boot devtools |

SPI 困境（第二次破坏的本质）：接口 `java.sql.Driver` 归 Bootstrap，实现在 `classpath` 只能由 Application 加载；委派链单向（[[双亲委派模型]]），Bootstrap **看不到**子层的类，模型无解。

## 线程上下文类加载器

TCCL 让父层加载器借线程上的变量拿到子层加载器：在单向委派链上开一条反向通道。

| API | 作用 |
|---|---|
| `Thread.currentThread().getContextClassLoader()` | 读当前线程绑定的加载器 |
| `Thread.currentThread().setContextClassLoader(cl)` | 绑定加载器到当前线程 |
| `ServiceLoader.load(Xxx.class)` | 内部用 TCCL 找 `META-INF/services` 实现 |

> [!warning] TCCL 要还原
> main 线程的 TCCL 默认是 `AppClassLoader`，新线程继承创建者的 TCCL；池化线程被改动后会复用给后续任务，`finally` 里不还原就表现为类找不到或加载到错误版本。

```java
// JNDI / SPI 标准写法：临时替换，用完必须还原
ClassLoader origin = Thread.currentThread().getContextClassLoader();
try {
    Thread.currentThread().setContextClassLoader(myClassLoader);
    ServiceLoader.load(Driver.class);
} finally {
    Thread.currentThread().setContextClassLoader(origin);
}
```

JDBC 4.0 起，`DriverManager` 静态块用 `ServiceLoader` + TCCL 扫 `META-INF/services/java.sql.Driver` 自动注册驱动，不必再 `Class.forName`（那条路靠静态块注册，初始化机制见 [[类加载过程]]）。

## 容器隔离案例

Tomcat 在委派链里插入「本地优先、再委派」的反向顺序，与默认模型的分叉点只在 WebApp 这一级：

| 加载器 | 职责 | 委派顺序 |
|---|---|---|
| Common | Tomcat 自身 + 所有 Web 应用共享的库（`lib/`，含 `servlet-api.jar`） | 标准委派 |
| WebApp | 单个应用 `/WEB-INF/classes` + `/WEB-INF/lib` | **本地优先**，找不到才委派 |
| Jasper | JSP 编译后的类，挂在 WebApp 之下 | JSP 改动即丢弃重建 |

- 层级树为 Bootstrap → System → Common → WebApp；Catalina / Shared 四层是老说法，现代默认只有 Common 一层（`server.loader` / `shared.loader` 是可选配置）。
- 每个 Web 应用一个 `WebAppClassLoader`，同名库的不同版本在各自命名空间下互不干扰（判据见 [[类加载器]]）。

> [!warning] 「本地优先」有强制例外
> `java.*`（沙箱保护）与 Jakarta EE API（Servlet / JSP / EL，来自 Common 的 `servlet-api.jar`）永远父优先，否则各 WebApp 各带一份同名 API、类型不兼容；整体切回父优先可配 `<Loader delegate="true"/>`。

```java
// WebAppClassLoader 简化示意（省略缓存命中与例外类判断）
Class<?> c = findLoadedClass(name);
if (c == null) {
    try { c = findClass(name); }                    // 1. 先找 WEB-INF
    catch (ClassNotFoundException e) { c = super.loadClass(name); } // 2. 失败才委派父
}
```

> [!danger] 热部署的本质是「换加载器」不是「换类」
> JVM 无法卸载单个类，只能连加载器一起回收：热部署 = 丢弃旧 `WebAppClassLoader`，让它的类与实例整体不可达再新建。代价是静态状态全部丢失，且**类加载器泄漏**（仍有引用指向旧加载器）是 `OutOfMemoryError: Metaspace` 的头号成因。

<details>
<summary>面试问答 (4题)</summary>

Q：为什么要破坏双亲委派？

A：三个场景：兼容 JDK 1.2 前重写 `loadClass` 的旧加载器；SPI 父层接口要加载子层实现（TCCL）；容器多版本隔离与热部署。

Q：线程上下文类加载器解决了什么问题？

A：父加载器看不到子加载器加载的类。TCCL 把子层加载器挂在线程上，`ServiceLoader` 取它加载 SPI 实现，绕开单向委派。

Q：Tomcat 为什么要自定义加载器？

A：隔离（各应用可用同名库的不同版本）、热部署（换加载器即整体替换）、共享（Common 层避免重复加载）。

Q：JDK 9 模块化后委派模型变了吗？

A：变了：先判模块归属，模块已定义给某个加载器则由它直接加载，不再一路向上问；`Extension` 也改名 Platform。

<details>
<summary>常见误区 (2条)</summary>

- 误区：破坏双亲委派是错误做法。它是有明确收益的设计选择，隔离与热部署都建立在其上。
- 误区：TCCL 是加载器继承链的反向指针。它只是 `Thread` 上的字段，与 `parent` 链无关，新线程默认继承创建者的 TCCL。

</details>
