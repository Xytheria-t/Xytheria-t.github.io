# 死锁

:::lede
死锁是一组线程互相持有对方所需资源又都不释放、导致全部永久阻塞的状态。
它需要互斥、占有且等待、不可抢占、循环等待四个条件同时成立。
**相邻概念：** 活锁在动但不前进 · 饥饿能拿到却总排不上
:::

## 思维链路速查

```chain
四条件 | 缺一不可 | 判定
复现现场 | 交叉持锁 | 代码
定位三板斧 | jstack/Arthas/自建检测 | 排查
破环策略 | 破任一条件 | 解法
面试问答 | 高频考点 | 复盘
```

死锁 = 多个线程互相持有对方要的锁,谁也不放 → 四个条件**同时成立**才可能发生 → 排查靠 Thread Dump 找环 → 解法是破坏任一条件,最常用固定加锁顺序与 tryLock 超时回滚。

## 四条件（缺一不可）

| 条件 | 含义 | 破坏手段 |
|---|---|---|
| 互斥 | 资源同一时刻只能一个线程持有 | 难破(锁的本质);改无锁 / 不可变 / 乐观读可绕开 |
| 占有且等待 | 持有一把锁还去申请下一把 | 一次性申请全部资源 |
| 不可抢占 | 已持的锁不能被强行抢走 | `tryLock(超时)` 主动释放已持有的锁 |
| 循环等待 | T1 等 T2 的锁,T2 等 T1 的 | **固定加锁顺序**(给锁编号,永远从小到大加) |

> [!note] 是必要条件,不是充分条件
> 四条同时成立也只是**可能**死锁,还要看调度时序是否真凑出环;反过来,只要死锁了,四条必然都成立。所以预防只需**破一条**。

## 复现：交叉持锁

- 生产上通常不是直白的两把锁,而是嵌套调用链(业务锁 → 数据库连接池锁 / 远程调用);`sleep` 只为把时序拉开、稳定复现,真实环境靠运气撞上,这正是死锁难查的原因。

```java
static final Object A = new Object(), B = new Object();
static void sleep(long ms) {
    try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
}

// T1：先 A 后 B
new Thread(() -> { synchronized (A) { sleep(100); synchronized (B) { } } }, "T1").start();
// T2：先 B 后 A —— 顺序相反即成环
new Thread(() -> { synchronized (B) { sleep(100); synchronized (A) { } } }, "T2").start();
```

## 定位三板斧

| 手段 | 命令 / API | 适用 |
|---|---|---|
| Thread Dump | `jstack -l <pid>` / `jcmd <pid> Thread.print` | 最通用,容器内也能用 |
| 一键找环 | Arthas `thread -b` | 线上最快,直接打印阻塞链 |
| 代码内自检 | `ThreadMXBean.findDeadlockedThreads()` | 想做定时巡检 / 自愈 |
| 事后回放 | JFR / async-profiler 锁事件 | 偶发、难复现 |

```chain
抓 dump | jstack -l pid > dump.txt | 第一步
找段落 | 搜 Found one Java-level deadlock | JVM 已代劳
配对锁 | waiting to lock ↔ locked | 连出环
回代码 | 按栈帧找嵌套锁 | 修
```

> [!tip] dump 里认这三行
> `Found one Java-level deadlock:` → 线程状态 `BLOCKED (on object monitor)` → 同一线程同时出现 `waiting to lock <0x...>`(想要的)与 `locked <0x...>`(已持有的)。把「谁 locked」和「谁 waiting to lock」连起来就是环。

偶发死锁要间隔 5s 抓 3~5 次,看 BLOCKED 的线程是不是**同一批**,排除「只是短暂竞争」。

## 破坏策略

| 破哪个条件 | 做法 | 代价 |
|---|---|---|
| 循环等待 | **固定加锁顺序**:给锁编号,永远从小到大加 | 首选,最省力;靠编码纪律 |
| 不可抢占 | `tryLock(超时)` ,超时就回滚并释放已持有的锁再退避重试 | 要写回滚与退避 |
| 占有且等待 | 一次性拿全(转账场景先锁"总账"或按序转账) | 并发度下降 |
| 互斥 | 改 [[CAS 与原子类]] / 不可变对象 / [[StampedLock]] 乐观读 | 只适合特定场景 |

超时后必须**释放已持有的锁 + 随机退避**再重试:不释放等于换个姿势继续抢,同步退避则退化成活锁。

## 相关故障对照

| 现象 | 线程状态 | 区别 |
|---|---|---|
| 死锁 | 永久 BLOCKED | 互相持有,谁也不放,CPU 通常不高 |
| 活锁 | 一直 RUNNABLE | 线程在动(不断重试 / 互相礼让),但整体不前进,CPU 可能打满 |
| 饥饿 | 长期 WAITING | 拿得到锁但永远排不上(非公平锁插队、读锁饿死写锁) |

> [!danger] 忘了 unlock 不是死锁
> 持有线程异常退出导致锁永不释放,其他线程无限 WAITING——**没有环**,dump 也不会标 deadlock。[[ReentrantLock]] 必须在 `finally{ unlock() }`。

<details>
<summary>面试问答 (3题)</summary>

Q：死锁的四个必要条件？

A：互斥、占有且等待、不可抢占、循环等待。四条同时成立才可能死锁,破坏任意一条即可预防。

Q：线上怎么定位死锁？

A：`jstack -l <pid>` 抓 Thread Dump,JVM 会直接打印 `Found one Java-level deadlock` 并列出 `waiting to lock` / `locked` 的锁 id;线上最快用 Arthas `thread -b`。

Q：怎么预防死锁？

A：首选固定加锁顺序(破循环等待),其次 tryLock 超时 + 回滚已持有的锁(破不可抢占);再辅以缩小锁粒度、缩短持锁时间、不在持锁期间调外部方法(开放调用)。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：四条成立就一定死锁。只是「可能」,还取决于调度时序是否恰好凑出环。
- 误区：死锁只发生在 synchronized。[[ReentrantLock]]、数据库行锁、分布式锁一样会成环,而 `jstack` 只能看到 JVM 内的锁。
- 误区：死锁一定伴随 CPU 飙高。阻塞在锁上的线程是 BLOCKED,不占 CPU;CPU 高更可能是活锁或自旋。

</details>
