# 阻塞队列

:::lede
阻塞队列（BlockingQueue）是在队列之上支持阻塞语义的接口：取元素时队列为空则等待其非空，入队时队列已满则等待空间可用，容量决定何时阻塞。
**边界：** 只做缓冲与背压 · 不负责线程创建与调度
:::

容量是队列唯一的硬约束:入队还是阻塞、扩容还是拒绝,全看它还剩几格;无界队列只剩「一直堆积到 OOM」。

## 常见实现

| 实现 | 特点 | 用途 |
|---|---|---|
| LinkedBlockingQueue | 可选有界 | FixedThreadPool 默认无界 |
| ArrayBlockingQueue | 有界、定长 | 固定容量 |
| SynchronousQueue | 不缓冲 | CachedThreadPool |
| DelayQueue | 延时 | 定时任务 |
| PriorityBlockingQueue | 优先级 | 按权重调度 |

> [!warning] 无界队列的代价
> 无界队列 + 持续提交 = 内存堆积,最终 OOM,这是 [[ThreadPoolExecutor]] 调参中最常见的坑;此类队列下 maximumPoolSize 也永不生效,线程数恒等于 corePoolSize。

- 队列满时线程数扩容到 maximumPoolSize,再满就触发 [[拒绝策略]]。
- 选型优先 ArrayBlockingQueue(有界、定长、内存可控),避免默认的无界 LinkedBlockingQueue。

## 落地：生产者消费者代码

阻塞队列在生产者/消费者间解耦:生产线程入队、消费线程从队首取,队空或队满时对应一方阻塞等待;队列容量直接决定 [[ThreadPoolExecutor]] 的扩容触发时机。整组队列工具属于 [[JUC]] 并发包。

```java
BlockingQueue<Runnable> queue = new ArrayBlockingQueue<>(100);
```

<details>
<summary>面试问答 (1题)</summary>

Q：为什么 FixedThreadPool 可能 OOM？

A：默认 LinkedBlockingQueue 无界，任务持续入队不触发拒绝，堆积耗尽内存。

</details>

<details>
<summary>容量估算参考</summary>

- 队列容量 ≈ 峰值 QPS × 平均耗时（短时突发可放大 1.5–2 倍）
- corePoolSize 估算见 [[ThreadPoolExecutor]]

</details>

<details>
<summary>常见误区 (2条)</summary>

- 误区：队列越大越安全。无界队列隐藏反压，任务堆积终致 OOM。
- 误区：SynchronousQueue 是"队列"。它不缓冲，提交即需有消费线程接手，否则建新线程或直接拒绝。

</details>
