# MySQL 索引

## 思维链路速查

```chain
索引是什么 | 空间与写放大换读 | 前提
分类两套坐标 | 物理 × 逻辑 | 结构
回表与覆盖索引 | 二级索引读路径 | 核心
联合索引 | 最左前缀 · 索引下推 | 设计
失效与 EXPLAIN | 验证与准则 | 实战
```

索引的收益全部来自「有序」：把数据按查询需要的顺序额外存一份，读时沿这份有序结构快速定位；代价同样来自这份额外结构——空间多一份、写多一层维护。B+ 树是承载这份有序性的结构（为什么是它，见 [[MySQL索引为什么用B+树]]）；而建一个索引到底赚不赚，取决于查询能否用上这份有序、以及回表代价可否接受——全文的设计准则都从这两点推出来。

## 前提：索引是什么，代价在哪

索引（Index）是存储引擎为加速查询而维护的**有序**检索结构，本质是空间换时间：

| 收益 | 代价 |
|---|---|
| 等值 / 范围查询从全表扫描 O(n) 降到树高 O(log n)，约 3~4 次 IO（树高 = 查询经历的 IO 次数） | 每个二级索引都是一棵独立的 B+ 树，占磁盘 |
| ORDER BY / GROUP BY 沿序直读，免排序 | INSERT / UPDATE / DELETE 要同步维护每棵索引树（写放大） |
| 唯一索引额外提供唯一性约束 | 索引多了优化器的选择成本也高，还可能选错 |

> [!warning] 索引不是越多越好
> 每加一个索引，写路径就多一棵要维护的 B+ 树。只有查询模式真实命中（WHERE / JOIN / ORDER BY 列）才值得建。

## 分类：物理与逻辑两套坐标

同一批索引，按「磁盘上怎么存」和「逻辑上起什么作用」各分一套，两套坐标可叠加（如「主键索引」物理上就是聚簇索引）。

物理分类（InnoDB 实现视角）：

| | 聚簇索引 | 二级索引（辅助索引） |
|---|---|---|
| 叶子存什么 | 整行数据 | 索引列值 + 主键值 |
| 每表数量 | 唯一一棵 | 想建几个建几个 |
| 本质 | 表数据本身按主键组织的 B+ 树 | 加速用的独立结构，查完常需回表 |

> [!note] 没有主键怎么办
> 聚簇索引的主键选择顺序：显式 PRIMARY KEY → 第一个 NOT NULL 的 UNIQUE 列 → 都没有则 InnoDB 生成隐藏的 6 字节 row_id。所以「无主键表」并非没有聚簇索引，只是用了你不可控的键。

逻辑分类（建索引用途视角）：

| 类型 | 写法 | 作用 / 限制 |
|---|---|---|
| 主键索引 | PRIMARY KEY | 唯一 + 非空，物理上就是聚簇索引 |
| 唯一索引 | UNIQUE KEY | 值唯一，允许多个 NULL（NULL 之间不判重） |
| 普通索引 | INDEX | 纯加速，无约束 |
| 联合索引 | INDEX(a, b, c) | 多列按声明序排序，遵守最左前缀，见下文 |
| 前缀索引 | INDEX(col(n)) | 只取字符串前 n 个字符建索引，省空间；不能用于覆盖与排序 |
| 全文索引 | FULLTEXT | 分词 + 倒排，适合大文本关键字检索，替代 LIKE '%x%' |

## 路径：回表与覆盖索引

二级索引的叶子里只有「索引列 + 主键」，要的列不在其中时，就得拿主键再走一遍聚簇索引——这一步叫回表（回聚簇索引取整行）：

```chain
查二级索引 | 按 name 定位，叶子拿到 id | 1 次树高
回表 | 拿 id 走聚簇索引取整行 | 2 次树高
覆盖索引 | 要的列索引里全有 | 停在第 1 步
```

覆盖索引（covering index）不是一种索引类型，而是**一次查询的状态**：SELECT 的列全部被某个索引覆盖（索引列 + 主键），这次查询就无需回表，EXPLAIN 的 Extra 显示 `Using index`：

```sql
-- 表：user(id 主键)，索引 idx_name(name)
SELECT id, name FROM user WHERE name = '张三'; -- 覆盖：id 是主键就在叶子里 → Using index
SELECT *      FROM user WHERE name = '张三';   -- 回表：其余列必须回聚簇索引取整行
```

> [!tip] 覆盖是给查询的奖励
> 索引建好时覆盖与否并不确定，取决于每条 SQL 取了哪些列。少 `SELECT *`、按需取列，才留得出覆盖的机会。

## 设计：联合索引与最左前缀

联合索引 (a, b, c) 的排序规则：先按 a 排，a 相同再按 b，b 相同再按 c。类比电话簿——先按姓排、姓相同再按名，「名」只在「姓」确定之后才有序。

以 INDEX(city, age) 为例，叶子按 (city, age) 排序（city 按字符序，示例取 北京 < 广州 < 杭州）：

| 叶子位次 | (city, age) | id |
|---|---|---|
| 1 | (北京, 20) | 7 |
| 2 | (北京, 35) | 3 |
| 3 | (广州, 18) | 5 |
| 4 | (广州, 30) | 2 |
| 5 | (杭州, 22) | 9 |

逐条对照，有序性能不能用一眼可判：

| 查询条件 | 能否用索引 | 原因 |
|---|---|---|
| city = '北京' | ✅ 定位 | 最左列全局有序 |
| city = '北京' AND age = 20 | ✅ 一步定位 | city 等值后，age 在区间内也有序 |
| city = '北京' AND age > 20 | ✅ 定位 + 范围 | 同上，age 可作范围 |
| age = 20 | ❌ | age 只在每个 city 内部有序，全局散乱（20、18、30、22…），无法定位 |
| score = 90 | ❌ | score 不在索引里 |

这就是**最左前缀原则**：只有从最左列开始**连续**命中，有序性才可利用。两点补充：

- 与 WHERE 书写顺序无关：`WHERE age > 20 AND city = '北京'` 优化器会整理条件顺序，仍可用索引；关键看条件是否覆盖了从最左列起的连续前缀。
- 范围截断：INDEX(a,b,c) 上 `a=1 AND b>2 AND c=3`，c 无法参与定位（b 是范围后，c 在区间内散乱），但可被索引下推用来过滤（见下）。

> [!note] 索引下推（Index Condition Pushdown，ICP）
> MySQL 5.6 引入。把「索引列上无法参与定位的过滤条件」下推到 InnoDB，在二级索引内部先判再回表，减少回表次数。例：INDEX(name, age) 上 `name LIKE '张%' AND age = 10`——无 ICP 时，'张%' 范围内逐条回表、server 层再过滤 age；有 ICP 时，age = 10 在索引内先判，只对通过的行回表。EXPLAIN 的 Extra 显示 `Using index condition`。

ORDER BY 同样守最左前缀：INDEX(a, b) 上 `ORDER BY a, b` 沿序直读；`ORDER BY b` 全局无序，只能 filesort（把结果集读进排序缓冲区再排，多一轮）。

## 实战：失效场景与 EXPLAIN

「索引失效」分两类，机理不同。

**结构性失效**——有序性前提被破坏，优化器没法用：

| 写法 | 破坏了什么 | 改法 |
|---|---|---|
| 列上函数 / 运算：`YEAR(t) = 2024`、`id + 1 = 5` | 索引存的是原值，加工后与索引值不可比 | 把条件改写到列上：范围 `t >= '2024-01-01' AND t < '2025-01-01'`、运算移到常量侧 `id = 4`；MySQL 8.0 也可建函数索引 |
| 隐式类型转换：phone 是 VARCHAR 却写 `phone = 13800001111` | 数字与字符串列比较时会把**列**转成数字（等价于 CAST 套在列上），同函数失效 | 常量写成 `'13800001111'`。反向（数字列配 `'5'`）转换落在常量上，不影响索引 |
| 最左不连续：INDEX(a,b) 只查 `b = 2` | b 全局无序 | 调整索引列序，或补上 a 条件 |
| 前缀模糊：`LIKE '%京'` | 起点不确定，无法在有序结构上定位 | 改前缀匹配 `'京%'`；尾缀 / 包含检索用全文索引 |

**成本性放弃**——索引用得上，但优化器按统计信息估算后认为不划算：

- 回表太多：命中行数占比大（如低区分度列）时，逐行回表不如一次全表扫描。区分度（selectivity）= `COUNT(DISTINCT col) / COUNT(*)`，越接近 1 越值得建独立索引，「性别」这类三值列单建无意义。
- 统计信息过期导致误判：`ANALYZE TABLE` 重新采样。
- `!=`、`NOT IN`、`IS NULL` 都不是必然失效——走不走取决于估算成本；InnoDB 二级索引的叶子里存有 NULL 值，`IS NULL` 可以走索引。

建没建、用没用，最终以 EXPLAIN 为准，重点盯四列：

| 列 | 看什么 | 参考值 |
|---|---|---|
| type | 访问类型（一次定位的成本） | 优 → 劣：const > eq_ref > ref > range > index > ALL；ALL = 全表扫描 |
| key | 实际选用的索引 | NULL = 没用上 |
| key_len | 联合索引用到第几列 | 判断最左前缀用到了哪 |
| Extra | 附加动作 | `Using index` = 覆盖索引；`Using index condition` = ICP；`Using filesort` / `Using temporary` = 额外排序 / 临时表，优化点 |

## 落地：建索引的准则

| 准则 | 机理 |
|---|---|
| 先看区分度再建 | `COUNT(DISTINCT col) / COUNT(*)` 接近 1 才值得；区分度低 = 命中大片行 = 回表不如全表 |
| 联合索引：等值列在前、范围列在后 | 等值确定后范围列仍有序；范围列之后的列只能靠 ICP 过滤 |
| 有 (a, b) 就别再建 (a) | (a, b) 的最左前缀就是 (a)，后者纯冗余，白付一棵树的写放大 |
| 长字符串用前缀索引 | 用 `COUNT(DISTINCT LEFT(col, n))` 找区分度拐点定 n；代价：无法覆盖、无法排序 |
| 按查询模式建，控制数量 | 每个索引一棵 B+ 树，写入全要维护；没被任何 SQL 命中的索引删掉 |
| 主键用自增 | 顺序写、页分裂少；UUID 随机写导致页分裂与碎片化，详见 [[MySQL索引为什么用B+树]]；分库分表后自增不再全局唯一，换分布式 ID，见 [[分库分表]] |

<summary>面试问答 (5题)</summary>

Q：什么是回表？怎么避免？

A：二级索引叶子只存「索引列 + 主键值」，查到后还要拿主键再走一遍聚簇索引取整行，这就是回表，等于多付一次树高的 IO。避免靠覆盖索引：让 SELECT 的列全部落在某个索引的「索引列 + 主键」范围内，EXPLAIN 的 Extra 显示 Using index。

Q：联合索引 (a, b, c)，哪些条件能用上？

A：从最左列开始连续命中：a、a+b、a+b+c 都可以；a 等值确定后 b 可用范围。跳过 a 单查 b 不行，因为 b 只在 a 确定后才有序。与 WHERE 书写顺序无关，优化器会整理等值条件的顺序；范围列之后的列无法参与定位，只能靠索引下推在索引内过滤。

Q：什么是索引下推（ICP）？

A：MySQL 5.6 引入的优化。把索引列上无法参与定位的条件（如范围列之后的等值、LIKE 前缀后的其他列条件）下推到 InnoDB，在二级索引内部先过滤再回表，减少回表次数。EXPLAIN 的 Extra 显示 Using index condition。

Q：唯一索引和普通索引怎么选？

A：查询上几乎无差：唯一索引命中即返回，普通索引会继续扫到第一条不满足的记录，量级可忽略。写入上普通索引更优：它可以把对索引页的修改先缓冲进 change buffer、延迟合并落盘，而唯一索引必须立即读页判重，用不上 change buffer。写多读少的表优先普通索引。

Q：索引失效有哪些场景？

A：分两类记。结构性失效（有序性被破坏，没法用）：列上函数或运算、隐式类型转换、不满足最左前缀、前缀模糊 LIKE '%x'。成本性放弃（能用但不划算）：低区分度列或命中行太多，回表总代价超过全表扫描。结论以 EXPLAIN 的 type / key / Extra 为准，不背清单。

<details>
<summary>常见误区 (4条)</summary>

- 误区：建了索引查询就一定走。优化器按成本估算决定；函数、隐式转换、低区分度都可能不用，一切以 EXPLAIN 为准。
- 误区：LIKE 一律失效。'京%' 前缀匹配可用索引定位，'%京' 尾缀匹配才不能。
- 误区：覆盖索引是一种索引类型。它描述一次查询的状态：SELECT 列被索引覆盖时，该查询即是覆盖查询。
- 误区：WHERE 条件顺序决定能不能走索引。优化器会整理 AND 条件顺序，关键是从最左列起连续有条件。

</details>
