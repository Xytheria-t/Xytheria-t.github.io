# MySQL 索引

## 思维链路速查

```chain
为什么是B+树 | 磁盘IO决定树高 | 结构
聚簇与二级索引 | 叶子存什么 | 分类
回表与覆盖索引 | 二级索引读路径 | 核心
联合索引 | 最左前缀 · 索引下推 | 设计
失效与EXPLAIN | 验证与建索引准则 | 实战
```

索引的收益与代价来自同一件事：为查询额外维护一份有序数据——读时沿序快速定位，写时多一棵树要维护。让这份有序落地的结构是 B+ 树，因为索引住在磁盘上、一次节点访问就是一页 IO，优化的目标是压低树高；叶子页里装「整行」还是「主键」，决定了回表与覆盖，也决定了最左前缀、失效与建索引准则这一整套用法。

## 结构：为什么是 B+ 树

索引常驻磁盘，访问一个节点 = 读一页（InnoDB 默认 16KB）= 一次 IO，所以衡量结构好坏的指标是**树高**（页访问次数），不是比较次数。

| 候选结构 | 致命短板 |
|---|---|
| 哈希索引 | 只支持等值，范围 / 排序 / 最左前缀全失效（仅 Memory 引擎与 InnoDB 自适应哈希辅助用） |
| BST / AVL / 红黑树 | 扇出恒为 2：千万行树高约 24~46 层（理想 24，最坏 2·log₂n≈46），每层一次随机 IO |
| B 树 | 非叶节点也存数据，单页容纳的键变少、树更高；范围查询要中序遍历整棵树 |
| **B+ 树** ✅ | 非叶只存键 → 高扇出；叶子成链 → 范围 / ORDER BY 顺链扫描 |

> [!tip] 扇出测算
> BIGINT 主键 8B + 指针 6B = 14B 一项，16KB 页约放 1170 个键；3 层 ≈ 1170³ ≈ 16 亿行，任意主键查找最多 3 次页访问。

叶子按索引列声明序全局排序——`(a, b, c)` 就是先按 a、a 相同再按 b，跳过 a 直接查 b 时 b 全局无序，这正是「最左前缀」的根源。对照：LSM 树（LevelDB / RocksDB）写友好但读要合并多层，按读写比选型。

## 分类：聚簇索引与二级索引

物理视角（InnoDB 实现）只有两种：

| | 聚簇索引 | 二级索引（辅助索引） |
|---|---|---|
| 叶子存什么 | 整行数据 | 索引列值 + 主键值 |
| 每表数量 | 唯一一棵 | 想建几个建几个 |
| 本质 | 表数据本身按主键组织的 B+ 树 | 加速用的独立结构，查完常需回表 |

聚簇索引的键按顺序选：显式 `PRIMARY KEY` → 第一个 NOT NULL 的 UNIQUE 列 → 都没有则 InnoDB 生成隐藏的 6 字节 row_id——「无主键表」只是用了不可控的键。

逻辑视角按用途分：

| 类型 | 写法 | 作用 / 限制 |
|---|---|---|
| 主键索引 | PRIMARY KEY | 唯一 + 非空，物理上就是聚簇索引 |
| 唯一索引 | UNIQUE KEY | 值唯一，允许多个 NULL（NULL 之间不判重） |
| 普通索引 | INDEX | 纯加速，无约束 |
| 联合索引 | INDEX(a, b, c) | 多列按声明序排序，守最左前缀（见下） |
| 前缀索引 | INDEX(col(n)) | 只索引前 n 个字符省空间；覆盖与排序用不上 |
| 全文索引 | FULLTEXT | 分词 + 倒排，替代 `LIKE '%x%'`，见 [[倒排索引]] |

## 回表与覆盖索引

二级索引叶子只有「索引列 + 主键」，要的列不在其中时得拿主键再走一遍聚簇索引——这就是回表：

```chain
查二级索引 | 按 name 定位，叶子拿到 id | 1 次树高
回表 | 拿 id 走聚簇索引取整行 | +1 次树高
覆盖索引 | 要的列索引里全有 | 停在第 1 步
```

覆盖索引不是索引类型，而是**一次查询的状态**：SELECT 的列全部落在某个索引的「索引列 + 主键」里，这次查询就无需回表，EXPLAIN 的 Extra 显示 `Using index`。是否覆盖取决于每条 SQL 取了哪些列——少 `SELECT *` 才留得出机会。

```sql
-- 表：user(id 主键)，索引 idx_name(name)
SELECT id, name FROM user WHERE name = '张三'; -- 覆盖：id 是主键就在叶子里
SELECT *      FROM user WHERE name = '张三';   -- 回表：其余列回聚簇索引取整行
```

## 联合索引与最左前缀

以 INDEX(city, age) 为例，叶子按 (city, age) 排，逐条对照一眼可判：

| 查询条件 | 能否用索引 | 原因 |
|---|---|---|
| city = '北京' | ✅ 定位 | 最左列全局有序 |
| city = '北京' AND age = 20 | ✅ 一步定位 | city 等值后，age 在区间内也有序 |
| city = '北京' AND age > 20 | ✅ 定位 + 范围 | 同上，age 可作范围 |
| age = 20 | ❌ | age 只在每个 city 内部有序，全局散乱（20、18、30…），无法定位 |
| score = 90 | ❌ | score 不在索引里 |

这就是**最左前缀**：只有从最左列开始**连续**命中，有序性才可利用。与 WHERE 书写顺序无关（`WHERE age > 20 AND city = '北京'` 优化器会整理条件顺序）；但范围会截断——INDEX(a,b,c) 上 `a = 1 AND b > 2 AND c = 3`，b 是范围后 c 在区间内散乱、无法参与定位，只能被索引下推用来过滤。

> [!note] 索引下推（Index Condition Pushdown，ICP）
> MySQL 5.6 引入。把「索引列上无法参与定位的过滤条件」下推到 InnoDB，在二级索引内部先判再回表。例：INDEX(name, age) 上 `name LIKE '张%' AND age = 10`，无 ICP 时逐条回表后由 server 层过滤 age，有 ICP 时 age 在索引内先判、只对通过的行回表。EXPLAIN 的 Extra 显示 `Using index condition`。

ORDER BY 同样守最左前缀：INDEX(a, b) 上 `ORDER BY a, b` 沿序直读；`ORDER BY b` 全局无序，只能 filesort（把结果集读进排序缓冲区再排，多一轮）。

## 失效场景与 EXPLAIN

「索引失效」分两类，机理不同。

**结构性失效**——有序性前提被破坏，优化器没法用：

| 写法 | 破坏了什么 | 改法 |
|---|---|---|
| 列上函数 / 运算：`YEAR(t) = 2024`、`id + 1 = 5` | 索引存的是原值，加工后与索引值不可比 | 条件改写到列上（`t >= '2024-01-01' AND t < '2025-01-01'`、`id = 4`）；8.0 也可建函数索引 |
| 隐式类型转换：phone 是 VARCHAR 却写 `phone = 13800001111` | 字符串列与数字比较会把**列**转成数字，等价于给列套函数 | 常量写成 `'13800001111'`；反向（数字列配 `'5'`）转换落在常量上，不影响索引 |
| 最左不连续：INDEX(a,b) 只查 `b = 2` | b 全局无序 | 调整索引列序，或补上 a 条件 |
| 前缀模糊：`LIKE '%京'` | 起点不确定，无法在有序结构上定位 | 改前缀匹配 `'京%'`；尾缀 / 包含检索用全文索引 |

**成本性放弃**——索引用得上，但优化器按统计信息估算后觉得不划算：命中行数占比大（低区分度列，区分度 = `COUNT(DISTINCT col) / COUNT(*)`）时逐行回表不如全表扫描；统计信息过期会误判，`ANALYZE TABLE` 重新采样。`!=`、`NOT IN`、`IS NULL` 都不是必然失效——看估算成本，InnoDB 二级索引叶子里存有 NULL，`IS NULL` 可以走索引。

EXPLAIN 重点盯四列：

| 列 | 看什么 | 参考值 |
|---|---|---|
| type | 访问类型（一次定位的成本） | 优 → 劣：const > eq_ref > ref > range > index > ALL；ALL = 全表扫描 |
| key | 实际选用的索引 | NULL = 没用上 |
| key_len | 联合索引用到第几列 | 判断最左前缀用到了哪 |
| Extra | 附加动作 | `Using index` = 覆盖；`Using index condition` = ICP；`Using filesort` / `Using temporary` = 额外排序 / 临时表，优化点 |

## 落地：建索引准则

| 准则 | 机理 |
|---|---|
| 先看区分度再建 | 越接近 1 越值得；区分度低 = 命中大片行 = 回表不如全表 |
| 等值列在前、范围列在后 | 等值确定后范围列仍有序；范围列之后的列只能靠 ICP 过滤 |
| 有 (a, b) 就别再建 (a) | (a, b) 的最左前缀就是 (a)，后者纯冗余，白付一棵树的写放大 |
| 长字符串用前缀索引 | 用 `COUNT(DISTINCT LEFT(col, n))` 找区分度拐点定 n |
| 按查询模式建，控制数量 | 每个索引一棵 B+ 树，写入全要维护；没被任何 SQL 命中的索引删掉 |
| 主键用自增 | 顺序写、页分裂少；UUID 随机写导致页分裂与碎片化（见 [[UUID]]）；分库分表后自增不再全局唯一，换分布式 ID（见 [[分库分表]]） |

> [!tip] 唯一索引 vs 普通索引
> 查询上几乎无差（唯一索引命中即返回，普通索引多扫一条不满足的记录，量级可忽略）；写入上普通索引更优——它能先把页改动缓冲进 change buffer 延迟合并，唯一索引必须立即读页判重，用不上缓冲（机制见 [[InnoDB]]）。写多读少的表优先普通索引。

<summary>面试问答 (3题)</summary>

Q：为什么索引用 B+ 树而不是红黑树 / 哈希？

A：索引在磁盘上，衡量标准是树高（= 页访问次数）而非比较次数：红黑树扇出恒为 2，千万行树高约 24~46 层，每层一次随机 IO；B+ 树单节点能放上千个键，3 层覆盖十亿行，查找最多 3~4 次页访问。哈希只支持等值，范围 / 排序 / 最左前缀全失效。

Q：联合索引 (a, b, c)，哪些条件能用上？

A：从最左列开始连续命中：a、a+b、a+b+c 都可以，a 等值确定后 b 可用范围。跳过 a 单查 b 不行，因为 b 只在 a 确定后才有序；范围列之后的列无法参与定位，只能靠索引下推在索引内过滤。

Q：自增主键和 UUID 主键哪个好？

A：各有权衡。自增主键顺序写入，页分裂集中在右端、局部性好，但高并发下右端成为争用热点；UUID 随机写入导致频繁页分裂与碎片化，且二级索引叶子要存主键，主键过长会撑大所有二级索引（见 [[UUID]]）。一般 OLTP 用自增，分库分表等需要全局唯一且避免自增泄露业务量的场景才用雪花 / UUID（见 [[分库分表]]）。

</details>

<details>
<summary>常见误区 (3条)</summary>

- 误区：索引越多查询越快。索引拖慢写入、占用空间；没人命中的索引应当删掉。
- 误区：建了索引查询就一定走。优化器按成本估算决定；函数、隐式转换、低区分度都可能不用，一切以 EXPLAIN 为准。
- 误区：覆盖索引是一种索引类型。它描述一次查询的状态：SELECT 列被索引覆盖时，该查询即是覆盖查询。

</details>
